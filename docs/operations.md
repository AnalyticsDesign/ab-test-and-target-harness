# 運用ガイド

エクスペリエンスを作り、本番に出し、様子を見るための手引き。デプロイ済みの環境([デプロイガイド](deploy.md))と、設置済みのサイト([サイト導入ガイド](site-install.md))があることが前提。

## 1. 用語の要約

画面の表記と、API・`CONTEXT.md` の英語の識別子の対応。運用で毎日使うものだけ。

| 画面の表記 | 英語の識別子(API・コード) | 1 行の定義 |
|---|---|---|
| **ワークスペース** | workspace | ユーザーとサイトを束ねる単位。メンバーはここで 1 つのロールを持つ |
| **サイト** | site(ID = サイト ID) | エクスペリエンスを配信する対象のサイト。導入の形(Deployment Mode)・同意の扱い(`consentMode`)・保存期間などの設定を持つ |
| **エクスペリエンス** | experiment | 1 つのテスト。複数のパターンに振り分けて比べる。対象 URL・配信条件・パターンを持ち、状態は 下書き / 配信中 / 一時停止 / 終了(`draft` / `running` / `paused` / `archived`) |
| **パターン** | variant | エクスペリエンスの中の 1 案(A パターン・B パターン)。重み(配分)と変更の集合を持つ |
| **変更** | change | ページへの 1 つの書き換え(`TEXT` / `IMAGE` / `HIDE` / `ATTRIBUTE` / `HTML` / `CSS` / `CUSTOM_JS`)。後ろ 3 つを**コードの変更**と呼ぶ |
| **目標** | goal | コンバージョンの定義(`PAGEVIEW` / `CLICK` / `CUSTOM`) |
| **オーディエンス** | audience | 名前を付けた訪問者の条件。サイトごとに作り、エクスペリエンスの配信条件で選ぶ。編集は次の公開で、参照するすべてのエクスペリエンスに効く |
| **公開** | publish | **サイト単位**の本番反映。そのサイトの配信中のエクスペリエンスすべてを 1 つの設定にまとめて配信に載せる |
| **開始 / 一時停止 / 再開 / 終了** | status を `running` / `paused` / `running` / `archived` に | 状態の変更。成功するとサイトを自動で公開する。終了は元に戻せない |
| **未公開の編集あり** | `unpublished` / `hasUnpublishedChanges` | 下書きに、まだ公開していない編集がある |
| **外部計測** | analytics | dataLayer に送る名札(GA4 などの外部の計測で使う)。エクスペリエンス・パターンの値とサイトの「外部計測の名前」 |
| **割当の固定** | `persistAssignment` | 初回の割当を訪問者ごとに保存し、配分を変えても再割当しない |
| **訪問者 ID** | identity(`idSource`) | 訪問者を見分ける ID の取り方(サイトの設定の節) |
| **オーナー / 管理者 / 編集者 / 閲覧者** | `owner` / `admin` / `editor` / `viewer` | ワークスペースでのロール |
| **システム管理者** | instance admin | この導入全体の管理者。すべてのワークスペースのオーナーを兼ねる |
| **API キー** | API key | エージェント・スクリプト用の鍵。**範囲**(すべてのワークスペース = `full` / 1 つのワークスペース = `workspace`)と**権限**(`roleCap`)を持つ |

関係は「ワークスペース ⊃ サイト ⊃ エクスペリエンス ⊃ パターン ⊃ 変更」。目標とオーディエンスはエクスペリエンスではなく**サイト**に属し、複数のエクスペリエンスから参照される。

### 状態(Desired Status)と公開済みの設定は別物

- **状態(Desired Status)** = 管理画面で設定したエクスペリエンスの状態(下書き / 配信中 / 一時停止 / 終了 = `draft` / `running` / `paused` / `archived`)。データベース上の値
- **公開済みの設定(config)** = 最後に成功した公開が配信に載せたもの。訪問者に実際に届いているのはこちらだけ

この 2 つがずれることがある。ずれ方は 2 通り。

- **開始・一時停止・再開・終了は、成功時にサイトを自動で公開する**ので、状態の変更は原則すぐ配信に反映される。自動の公開が失敗したときだけ、状態は 一時停止(`paused`)なのに配信は 配信中(`running`)のまま、といった差が残る(エクスペリエンス一覧の「本番」の列に「未反映」と出て、ポイントすると「配信中: 配信中(一時停止 は未反映)」のように差が出る。公開で再試行する)
- **変更・パターン・配信条件・目標を編集しただけでは公開されない**。下書きは安全に貯まるだけで、訪問者には届かない。届けるには**公開**を押す(管理者以上)

「管理画面で直したのに本番が変わらない」の大半はこの 2 つ目である。

## 2. エクスペリエンスのライフサイクル

1. **作成**(編集者以上): 対象のワークスペース → サイト → エクスペリエンスを新規作成する。パターン a / b が 50:50 で自動生成される
2. **編集**(編集者以上): パターン・変更・配信条件・目標を編集する。**コードの変更を含むあらゆる下書きを編集者が作れる**。保存しても下書きのままで、訪問者には届かない
3. **下書きの確認**([3 節](#3-下書きプレビュー)): 対象ページで実際の見た目と適用結果を見る
4. **開始**(管理者以上): 下書き → 配信中(`draft → running`)。成功すると**サイトが自動的に公開される**
5. **一時停止 / 再開**(管理者以上): 配信中 ↔ 一時停止(`running ↔ paused`)。これも自動の公開を伴う
6. **終了**(管理者以上): 配信中・一時停止 → 終了(`running | paused → archived`)。**元に戻せない**。同じ内容でやり直すときは新しいエクスペリエンスを作る

**ID は作成後に変更できない**(エクスペリエンス / パターン / 目標 / オーディエンス)。とくに `experimentId` は割当ハッシュの入力なので、作り直すと全訪問者の割当が変わる。

### 未公開の編集の見え方

最後に成功した公開以降に編集があると、管理画面が 3 か所で知らせる。

- **エクスペリエンス一覧**: そのエクスペリエンスに「未公開の編集あり」バッジ
- **上部バー**(サイトの中のどの画面にも出る): 「未公開の編集あり」の表示と、強調された「公開」ボタン(目標・オーディエンス・タイムゾーンの変更はサイトのレベルで拾う)
- **公開の確認画面**(上部バーの「公開」を押すと開く): 前回の公開以降に変わったエクスペリエンス / 変更の一覧(誰が・いつ・コードの変更には「コードを含む」の印)。公開する前にここを読む

一度編集して元に戻しただけでも「未公開の編集あり」と出る(内容の比較まではしない)。

### 公開はサイト単位

公開は、そのサイトの**配信中のエクスペリエンスすべて**を 1 つの設定にまとめる。したがって「エクスペリエンス X の修正だけを出す」ことはできず、公開した時点で**ほかのエクスペリエンスの未公開の編集も一緒に出る**。複数人で触るサイトでは、公開の確認画面の変更サマリを毎回読むこと。

公開は失敗しても旧 version が配信され続ける(activation の前に落ちるため)。失敗した回は公開履歴に `failed` として残る。

### オーディエンスと配信条件

**オーディエンスの作り方**: サイトの「オーディエンス」→「新しいオーディエンス」を開き、左の部品をドラッグして条件を組み立てる(部品をクリックすると一番外側のグループに入る)。グループは「すべて満たす / いずれかを満たす」と「除外する」を選べる。入れ子は一番外側のグループの中に 4 段まで。既存のオーディエンスを取り込むと、その時点の定義のコピーが入る(元のオーディエンスを後から変えても連動しない)。

**エクスペリエンスの配信条件**: 1 段の「すべて満たす / いずれかを満たす」に条件の行を並べる。行の種類に「オーディエンス」があり、入れ子や除外が要る条件はオーディエンスで作って選ぶ。

**閲覧したページの条件**: URL / パス / ホストを直接書く。同じ一致の仕方(部分と演算子と値)なら、回数や期間を変えても閲覧回数は共有される。一致の仕方を変えると別のページの条件になり、閲覧回数は数え直しになる。

**期間の条件**: 閲覧・目標の「最後の閲覧・達成が N 日以内」「過去 N 日に閲覧していない」の N は、訪問者データの保存期間(`retentionDays`)以下にする。保存期間を短くするときは、先に条件の期間を直して公開する(期間が保存期間を超える条件が残っていると、保存期間の変更は 422 で止まる)。

**編集と公開**:

- 配信中のエクスペリエンスが使っているオーディエンスを保存しようとすると確認が出る。編集は次の公開で、参照するすべてのエクスペリエンスに効く
- 公開の確認画面に「オーディエンスの変更」(配信対象が変わるエクスペリエンス)・次の公開で数えるのをやめるページの条件・画面の幅の条件についての注意・公開で止まる理由が出る
- 配信条件から参照されているオーディエンスと、オーディエンスから参照されている目標は削除できない

**アクセシビリティ設定**: ユーザーメニュー →「設定」→「画面表示」の「ドラッグの代わりにボタンで操作する」をオンにすると、「ここに追加」・↑↓・「移動先」で条件を並べ替えたり、グループの間で動かしたりできる(設定はこのブラウザだけに保存される)。オフのときは、オーディエンスの作成と配信条件の画面の条件の下に、この設定への案内が出る。

#### 配信条件の正規表現

管理画面の正規表現の入力欄の案内が、この節を参照する。

- 使えるのは**パスとホストだけ**。URL 全体には使えない(「ホストが一致」+「パスが正規表現に一致」で書き換える)
- **部分一致**。全体に一致させるときは `^` と `$` を付ける
- 使える書き方:

| 書き方 | 意味 |
|---|---|
| ふつうの ASCII 文字 | その文字 |
| `\.` `\/` `\-` `\?` `\*` `\+` `\(` `\)` `\[` `\]` `\{` `\}` `\^` `\$` `\\` と、`\` に縦線を続けた形 | 記号そのもの |
| `.` | 任意の 1 文字 |
| `[...]` / `[^...]` | 文字クラス / その否定 |
| `\d` `\w` `\s` | 数字 / 英数字と `_` / 空白 |
| `^` `$` | 先頭 / 末尾 |
| `( )` `(?: )` と縦線 | グループ / 選択 |
| `?` `*` `+` `{n}` `{n,m}` | 繰り返し(`m` は 100 まで) |

- 使えないもの: 後方参照、先読み・後読み、名前付きグループ、フラグ、上限のない `{n,}`、最短一致(`*?` など)
- 上限: 式は 200 字まで、1 つの正規表現は 200 命令(変換後の大きさ。`{n,m}` は展開して数える)まで、サイト全体で 500 命令まで。超えると公開が止まる。数え方は次のとおり
  - パス・ホストの条件の正規表現は、オーディエンスを複数のエクスペリエンスで使うと**参照の数だけ**サイト全体の命令数に数える(エクスペリエンスごとに配る設定へ写り、別々に照合されるため)
  - 閲覧したページの条件の正規表現は、同じ一致の仕方なら何件から使っても 1 つと数える
- 大文字と小文字を**区別する**。ホストは小文字にして照合するので、式のホストも小文字で書く
- `¥`(円記号)と全角の文字は、`\` と半角に置き換えられる。日本語のパスは `%E3%81%82` のようにエンコードした形で書く
- 照合するパスが 256 字を超えるページでは判定しない(そのページでは、パスの正規表現を含む条件を使うエクスペリエンスは対象外になる)
- 管理画面の「試す」欄に値を入れて、一致するかを確かめられる

## 3. 下書きプレビュー

対象ページを `#__ab_preview=<experimentId>:<variantId>` 付きで開くと、指定したパターンを強制的に見られる(認証不要)。複数指定はカンマ区切り: `#__ab_preview=exp_a:b,exp_b:a`。

**プレビューは完全隔離モード**で、指定したエクスペリエンスだけを適用し、**Cookie・consent・decision 通信・目標・Exposure に一切触れない**。したがって計測に混ざらない代わりに、**Exposure の確認には使えない**([5 節](#5-開始直後のチェック))。

### `AB.getPreviewReport()` の読み方

プレビュー中は Console で `AB.getPreviewReport()` が変更ごとの適用結果を返す(通常表示では常に `null`)。

| フィールド | 見方 |
|---|---|
| `matched` | selector に一致した要素数。**0 なら selector が外れている**(ページ構造が変わった / タイポ / 描画前) |
| `applied` | 適用に成功したか |
| `error` | 適用時の例外メッセージ。**CSP でブロックされた CUSTOM_JS はここに出る** |

エクスペリエンス単位の `error` は 3 種類ある(いずれも `changes: []` で、適用も割当もされない)。

- `unknown experiment or variant`: 指定したエクスペリエンス / パターンが配信 config に無い
- `invalid preview request`: フラグメントの書式が壊れている(`エクスペリエンス ID:パターン ID` になっていない・空)
- `duplicate experiment`: 同じエクスペリエンスを 2 回以上指定した(2 回目以降がこれになる)

**コードの変更を含むエクスペリエンスは、開始する前にここで `error` が空であることを確認する**。

### 未公開の下書きを本物のページで見る

公開されていない下書きはプレビューだけでは見られない(配信 config に載っていないため)。エージェント面の `GET …/draft-bootstrap` が返す JS をページに注入する([エージェント向けガイド レシピ 2](agent-guide.md#レシピ-2-下書きを検証する公開前に本物のページで見る))。

> **注意**: `draft-bootstrap` が返すのは設置タグのファイルと同形式の**完全に機能する bootstrap** で、隔離されるかどうかは URL に `#__ab_preview=` フラグメントがあるかどうかだけで決まる。**フラグメント無しの URL に注入すると下書きが本番として動く** — 未公開のエクスペリエンスが実際に適用され、Cookie が作られ、`ab_exposure` が計測に混ざる(GA4 が汚れる)。注入したページは必ず `#__ab_preview=<experimentId>:<variantId>` 付きの URL で開くこと。

## 4. 公開の反映

公開から訪問者のブラウザに届くまでは **1 分ほど**。内訳は次の 2 つが積み重なる。

| 要素 | 最大 |
|---|---|
| 配信ファイルの更新(デプロイ専用の Worker が設置タグのファイルを作り直す。公開の結果の `staticDeploy` に出る) | 数秒 |
| ブラウザのキャッシュ(`Cache-Control: public, max-age=60`) | 60 秒 |

公開直後に本番を見て「変わっていない」のは、たいていこのブラウザのキャッシュの待ち時間である。反映の確認は次で早い。

```bash
curl -s "https://<設置ホスト>/s/<siteId>.js" | head -c 300
```

先頭のコメント行が `/* Web Test and Target Harness bootstrap (site <siteId>, config v<version>, runtime <ハッシュ>) */` の形で、`v<version>` が公開した版になっていれば反映済み。古い番号のままなら、まだ配信ファイルが更新されていない(下の警告を見る)。

**設置タグのファイルの更新が済んでいないとき**: 公開は成功(`ok: true`)でも、配信ファイルの更新だけが遅れる・失敗することがある(公開の結果の `staticDeploy` が `pending`)。このとき管理画面のサイトの上部に「設置タグの配信ファイルが最新の公開内容になっていません」の警告が出る。デプロイ専用の Worker が失敗を自動で再試行する(30 秒・2 分・10 分、以後 1 時間ごと)ので、たいていは待てば直る。続くときは、管理者以上が警告の「配信ファイルを作り直す」を押す(API は `POST /sites/<siteId>/static/redeploy`)。更新が済むまでは、前に作った配信ファイルが訪問者に届く(初めての公開でまだ無いときは、タグが読み込まれない)。サイトの設定(訪問者 ID・外部計測の名札)を保存したときも、配信ファイルを自動で作り直す(公開は不要)。

runtime を新しい版に更新したときも、デプロイ専用の Worker が次の公開か、遅くとも 1 時間以内に全サイトの配信ファイルを作り直す。作り直しの間に前の runtime のファイルが残っても、サイトは動く。

**ゾーンの Cache Rule は念のための設定**(必須ではない)。ゾーンの Browser Cache TTL(既定 4 時間のプランがある)が、ゾーンのキャッシュに当たった応答の `Cache-Control` を上書きする場合、戻り訪問者のブラウザが古い設定を最大 4 時間使い続ける。実機では配信ファイルの応答は上書きされなかったが、プランやゾーンの設定で変わりうるので、`/s/*` を Cache Rule で切り離してヘッダを尊重させておく。手順は [デプロイガイド 2 節](deploy.md#2-edge-のデプロイ)の 2.6。

## 5. 開始直後のチェック

開始したら**その場で対象ページを Chrome で開く**。見るのは 4 点。

1. **対象 URL で適用されている**: パターンの変更が実際に見えること。出ないときは [10 節](#10-トラブルシュート)
2. **Console に CSP / Trusted Types の違反が無い**([サイト導入ガイド 10 節](site-install.md#10-コードの変更と-csp))
3. **`ab_exposure` が届いている**: `dataLayer` か GA4 の DebugView で確認する([サイト導入ガイド 5 節](site-install.md#5-設置後の確認))
4. **コードの変更を含むエクスペリエンスは、開始前にプレビューで `error` を確認済みである**([3 節](#3-下書きプレビュー))

### コードの変更を含むエクスペリエンスの必須手順

CUSTOM_JS だけのパターンが CSP でブロックされると、**処理群だけ Exposure が出ず**(対照群は selector で出る)、母数が片側に偏る(SRM)。これはコード側では検知できないので、運用手順で担保する。

コードの変更(HTML / CSS / CUSTOM_JS)を含むエクスペリエンスは、**開始直後**に対象ページを Chrome で開き、次を確認する。

- **(a)** Console に CSP / Trusted Types の違反が無いこと
- **(b) 両群**の `ab_exposure` が出ること。割当を引き直す方法は Mode で違う: Mode A は `_ab_vid`(既定の正本 Cookie 名)を削除して再読込、Mode C は参照 Cookie の値が違う別のテスト利用者で開く(本番の認証 Cookie は消さない)、D-lite は DevTools → Application → Cookies で HttpOnly の正本 Cookie を削除する([サイト導入ガイド 5 節](site-install.md#5-設置後の確認))。**エクスペリエンスに設定した全パターンが出るまで踏む**。確認は `dataLayer` か GA4 の DebugView
- **(c)** 違反・片群の Exposure 欠落・変更の適用失敗のいずれかがあれば**即、一時停止**する。原因を直し、再検証してから再開する

**下書きプレビューは Exposure を送らないので、(b) の代わりにはならない**([3 節](#3-下書きプレビュー))。プレビューは「適用できるか」を見る道具、開始直後のチェックは「両群に届いているか」を見る道具である。

### 出ない理由を機械的に調べる

「なぜこの URL でこのエクスペリエンスが出ないのか」は、`evaluate`(割当の dry-run)がエクスペリエンスごとに `reason` を返す。使い方は [エージェント向けガイド レシピ 4](agent-guide.md#レシピ-4-配信条件の-what-ifなぜこの-url-で出ないのか)。

## 6. ロールと管理操作

### システム管理者

この導入(Cloudflare アカウント上の 1 デプロイ)全体を管理する人。**初回セットアップで作った最初のオーナーがシステム管理者になる**。システム管理者は、すべてのワークスペースのオーナーを兼ね(新しいワークスペースができると自動でオーナーとして入る)、次の操作を行える:

- **ワークスペースを作る・削除する**(システム管理者だけ。ワークスペースのオーナー / 管理者でも、システム管理者でなければ作れない・削除できない。ユーザーメニュー →「設定」→「ワークスペース」。一覧にサイト・メンバー・配信中の数が出る。削除はワークスペース名を打ち込んで確かめてから行い、配信中のエクスペリエンスがある・最後の 1 つのときはボタンが押せず理由が出る。API は `POST /workspaces` / `DELETE /workspaces/:wid`)
- **システム管理者を追加する・外す**: ユーザーメニュー →「設定」→「システム管理者」(管理画面からだけ。API キーでは行えない)。追加はワークスペースのメンバーの一覧から選ぶ(各行に参加しているワークスペースとそこでのロールが出る。まだメンバーでない人・メンバーから外した人は選べないので、先にワークスペースへ招待して受諾してもらう)。追加した人はすべてのワークスペースのオーナーになり、その人宛ての未受諾の招待は取り消される。外すと、その人が**システム管理者になる前に参加していたワークスペースでは元のロールに戻り**、それ以外のワークスペースからは外れる(確認画面に戻るワークスペースとロールが出る。最初のシステム管理者のように、なる前の参加の記録が無い人はすべてのワークスペースから外れるので、必要なら改めて招待する)。完全に外したいとき(退職など)は、確認画面で「元のロールに戻さず、すべてのワークスペースから外す」にチェックを入れる。最後の 1 人は外せない(409 `last_instance_admin`)

ワークスペースの側からシステム管理者に手を出すことはできない: メンバー画面ではシステム管理者の行に印が付き、ロールの変更・削除はできない(409 `instance_admin_member`)。システム管理者宛てのリセットリンクの発行と、システム管理者の API キーの失効も、システム管理者だけが行える(鍵は「メンバーの API キー」の一覧に「システム管理者」の印付きで出る)。

**システム管理者は 2 人以上にしておく**。1 人だけでその人の Google アカウントが使えなくなると、非常用の経路(デプロイガイド 8 節)でしか戻れない。

人ごとに見せるサイトを分けたいときは、ワークスペースを分けて、それぞれに必要な人だけを招待する(ロールはワークスペースごと)。

### ロール

| 操作 | オーナー | 管理者 | 編集者 | 閲覧者 |
|---|---|---|---|---|
| ワークスペースの作成・削除(システム管理者だけ。上の「システム管理者」の節) | — | — | — | — |
| ワークスペース / メンバーの管理、招待の発行・取り消し | ○ | ○ | × | × |
| サイトの作成・設定変更(mode / id_source / allowed_origins / retention / consentMode / forgetOnRevoke) | ○ | ○ | × | × |
| 外部計測の名前のサイト単位(イベント名・キー名・`extraKey`) | ○ | ○ | × | × |
| エクスペリエンス・パターン・変更・目標の作成・編集(**コードの変更を含む**) | ○ | ○ | ○ | × |
| **本番化: 公開・開始・一時停止・終了** | ○ | ○ | × | × |
| 結果(GA4 リンク)閲覧 | ○ | ○ | ○ | ○ |
| サイトの削除 | ○ | × | × | × |

**ワークスペースを削除できるのはシステム管理者だけで、最後に残った 1 つは削除できない**(409 `last_workspace`)。配下のサイトの設置タグの配信ファイルも消す。消せないときはワークスペースを削除せずに 503 `static_remove_failed` を返すので、しばらくしてからやり直す(サイトの削除と同じ扱い。上の「サイトの削除」。削除が受け付けられた後に配信ファイルが実際に消える時期も、サイトの削除と同じ)。**配下のサイトに実行中のエクスペリエンスがあるワークスペースも削除できない**(409 `workspace_has_running_experiments`。先にすべて終了する)。すべて消すと誰もログインできない状態になるため、その一手前で断る。作り直したいときは先に新しいワークスペースを作り、それから古い方を削除する。ワークスペースを削除すると、そのワークスペースにしか所属していなかった人はその場でログイン状態が切れる。

境界は「作成」と「本番化」で引く。編集者はコードの変更を含むあらゆる下書きを作れるが、訪問者に届く操作(公開と状態の変更)は管理者以上に限る。編集者の資格で公開・開始を呼ぶと 403(`{"error":"forbidden","required":"admin","hint":"…"}`)になる。

### API キー

**大原則: 人とアクセス権の書き込みは管理画面から行う**。API キーの発行・一覧・失効、招待の発行・取り消し・受諾、メンバーのロールの変更・削除、リセットリンクの発行、システム管理者の追加・外す、ワークスペースの作成・削除、ログインの操作は、API キーでは行えない(403 `session_required`。鍵の種類に関わらない)。漏れた鍵で鍵を増やす・自分を招待して居座る・他人のパスワードを変える・ワークスペースを消す、を防ぐため(鍵を失効させても、増やした鍵や招待で入ったメンバーは残る)。API キーはサイト・エクスペリエンスの運用(作る・直す・公開する・読む)に使う。読み取り(メンバー・招待の一覧など)は鍵でもできる。

管理画面のユーザーメニュー →「設定」→「API キー」の「新しい API キーを発行」で発行する。項目は 4 つで、すべて選ぶまで発行できない: **名前**(どこで何に使うキーか)/ **範囲**(**ワークスペース** = 選んだ 1 つだけで使える。そのワークスペースのメンバーなら発行できる。**すべてのワークスペース**(API の値は `full`)= システム管理者だけが発行・使用できる)/ **権限**(閲覧者 / 編集者 / 管理者 / 本人と同じ。範囲での自分のロール以下だけが選べる。API の `roleCap`)/ **有効期限**(期限なし / 1 日 / 7 日 / 30 日 / 90 日。期限は発行した時刻から数え、選ぶと期限の日時が横に出る。API の `expiresInDays` は 1〜365 の整数で、省略すると期限なし。更新や確認のためだけに使う鍵は 1 日にする。期限を過ぎた鍵は 401)。一覧の「期限」の列に期限の日時(過ぎた鍵は「期限切れ」)が出る。範囲外のワークスペースは鍵からは見えない(404)。キーの実際の権限は **そのワークスペースでの持ち主のロールと、選んだ権限の低い方** になる(権限は付与ではなく、ロールより上には行かない。ロールが下がればキーの権限も下がる)。**キーは発行の直後に 1 度だけ表示され**、「保管したので閉じる」を押すまで次の発行はできない(控えずに別の画面へ移ろうとすると確認が出る)。以後はハッシュしか保持しないので、控え忘れたら失効させて発行し直す。鍵は、持ち主が範囲を使えなくなると(すべてのワークスペースの鍵 = システム管理者から外れた、ワークスペースの鍵 = そのワークスペースから外れた・ワークスペースが削除された)その時点から 401 になる。エージェントに下書きだけ作らせるなら、権限を「編集者」にする。誰の操作かをメンバーの一覧で見分けたいときは専用のユーザーを作り(専用の Google アカウントのメールアドレスで招待する)、そのユーザーで発行する。**管理者以上は、ワークスペースのサイドバーの「メンバーの API キー」で、そのワークスペースで使えるキー(そのワークスペースの鍵と、システム管理者の「すべてのワークスペース」の鍵)を持ち主・範囲・権限・最終使用日付きで一覧でき、失効させられる**(自分のキーの画面の下にも、管理者以上であるワークスペースへのリンクが出る。API は `GET /workspaces/:wid/api-keys` / `DELETE /workspaces/:wid/api-keys/:kid`)。「すべてのワークスペース」の鍵を失効させると、どのワークスペースでも使えなくなる。オーナーのキーを失効できるのはオーナーだけ。失効させた鍵と期限を過ぎた鍵は、使えなくなった時刻(失効か期限切れの早い方)から 30 日間一覧に残り(失効させた鍵は「失効済み」に名前・接頭辞・発行日・失効日、期限を過ぎた鍵は期限の列に「期限切れ」。接頭辞はどの鍵も同じ `wtt_` で、鍵そのものは分からない)、その後は自分の一覧を開いたときに消える。失効した鍵はその時点から認証に通らない(失効の記録は鍵の行とは別に持つので、失効と同時に使われていた要求があっても失効は消えない)。

### ログイン

管理画面へのログインは **Google アカウント**で、入れるのは招待されたメールアドレスだけ。受け取るのはメールアドレスとプロフィールだけで、**Google のトークン(アクセストークン・ID トークン)は保存しない** — ログイン後に Google の API を呼ばないため。メール + パスワードの経路は普段閉じており、開いているあいだは、管理画面にログインしているあいだどのページにも注意の帯が出る(ログイン前の画面には出ない)。

### メンテナンス中(書き込みの凍結)

更新などの間、管理画面の上部に「メンテナンス中のため、変更は保存できません」の帯が出る。この間は保存・公開・エクスペリエンスの開始と一時停止・招待の受諾などができない(押すと理由が表示される。入力は消えない)。閲覧とログインはでき、訪問者への配信も続く。帯が消えてから(開いたままの画面でも 1 分ほどで消える)、もう一度保存する。エクスペリエンスの編集画面で「一部は保存されています」と出た場合も、画面を再読み込みせずに、帯が消えてからもう一度保存すると残りも保存される。帯が「再開の見込みを過ぎています」のまま続くときは、更新の作業者に確認する(凍結は作業者が外すまで続く)。

### ログインできなくなったとき

- **メンバーが入れない**: 通常は Google アカウント側の問題なので、Google の復旧手順で直す(パスワード再設定、2 段階認証の端末変更など)。招待されたメールアドレスと違う Google アカウントでは入れない
- **「どのワークスペースにも所属しておらず、有効な招待もありません」と出る**: ログイン画面に出るこの文言は、(a) そのメールアドレスが招待されていない(招待されたのと違う Google アカウントで入ろうとした場合を含む)、(b) メンバーから外された・招待を取り消された、のどちらかである。心当たりが無ければ、ワークスペースのオーナー・管理者に、そのメールアドレス宛ての招待を発行してもらう。非常用のパスワードログインが開いているときも、同じ理由なら同じ文言で断られる(パスワードの誤りではない)
- **オーナーが入れない**(OAuth クライアントを消した・壊した、Google 側の障害): [デプロイガイド 8 節「非常時の入り方」](deploy.md#8-非常時の入り方)。Cloudflare で control の secret を設定できる人だけが、非常用トークンでオーナーのパスワード再設定リンクを得られる。用が済んだらトークンを消す
- **非常用の経路が開いているあいだのパスワードリセット**: メール送信基盤は持たない。対象ユーザーが所属するワークスペースの**メンバー画面で、その人の行の「リセットリンク」**を押し、発行されたリンクを本人に手渡しする(発行先のワークスペースで管理者以上の人が、発行先だけに所属する人か自分自身に発行できる。対象が他のワークスペースにも所属するときは、そのすべてでオーナーの人かシステム管理者だけが発行できる。オーナー宛のリンクを発行できるのはオーナーのみ。再設定すると、その人のそれまでのログイン状態はすべて切れる。招待を受けたりロールが変わったりすると、その前に発行されたリンクは使えなくなる)。リンクは管理画面の `/reset?token=…` 形式。非常用の経路が閉じているときは発行できない(409 `password_login_disabled`)。リンクを開いて失敗するときは、まず再設定画面の案内どおり URL が途中で切れていないか(末尾までコピーしているか)を確認する。それでも開けなければ期限切れか使用済みなので、リンクを発行し直す

### 招待

招待リンクは**発行から 7 日で失効する**。メールは送らないので、発行者が手渡しする。受ける側は、**招待されたメールアドレスと同じ Google アカウントでログインして**受諾する(別のメールアドレスの Google アカウントでは受けられない)。

- **いつ切れるかを見る**: 招待一覧の「期限」列に、切れる日時(見ている人のタイムゾーン)と残り(「あと 3 日」「あと 5 時間」など)が出る。期限は**発行または延長した時刻から 7 日ちょうど**で切れる(その日の終わりではない)
- **期限を延ばす**: 招待一覧の「期限を延ばす」を押すと、その時点から 7 日後まで延びる。**リンクは変わらない**ので、相手に渡し直す必要はない。既に切れている行のボタンは「発行し直す」になり、こちらは**新しいリンク**になる(古いリンクは使えない。渡し直すこと)。同じメールアドレス・同じロールでもう一度「招待リンクを発行」しても同じ結果になる
- **ロールを変えたい**: **先にその招待を取り消してから、新しいロールで発行し直す**。既に招待済みのメールアドレスを違うロールで招待しようとすると、現在のロールを示して断られる(API では 409 `already_invited`)。黙ってロールが変わらないまま期限だけ延びることはない
- **招待された人がログインしたのにワークスペースが何も出ない**: 招待リンクを開かずに、ログイン画面から直接ログインしている。招待されたメールアドレスならログイン自体は通るが、**ワークスペースに入るのは招待リンクを開いて「この招待を受ける」を押したとき**である。この状態ではホームに「まだどのワークスペースにも参加していません」という案内が出るので、招待リンクを開き直すよう伝える。ログインしたまま招待リンクを開き直せば受諾できる。招待を渡すときは「このリンクから入ってください」と添える
- **発行した招待を取り消す**: **オーナー・管理者**が、ワークスペースのメンバー画面の招待一覧にある「取り消す」で行う(API では `DELETE /workspaces/:wid/invitations/:id`)。取り消した招待のリンクはその場で使えなくなり、一覧からも消える。一覧に並ぶのは**まだ受けられていない招待だけ**で、受諾済み・取り消し済みの招待は出ない。メールアドレスを間違えて発行したときは、取り消してから正しいアドレスで発行し直す
- **メンバーから外す / 招待を取り消すと、その人はログインできなくなる**: 他のワークスペースに所属しておらず、別の有効な招待も無ければ、その時点で**ログイン中の状態もその場で切れ**(次の操作から画面がログインに戻る)、以後は新しくログインすることもできない。API キーも同じで、ワークスペースに触れない。他のワークスペースに所属している人・別の有効な招待がある人のログイン状態は切れない。外した人を戻すときは招待し直す

### サイトの削除

**オーナーのみ**。サイトの設定の変更が管理者以上なのに対し、削除は取り返しがつかないので一段絞ってある。**配信中のエクスペリエンス(状態または公開済みのいずれかが `running`)があるサイトは削除できない**(409 `site_has_running_experiments`)。先に終了してから削除する。削除しても Visitor Profile は即時には消えない([8 節](#8-既知の制約))。

設置タグの配信ファイルも消す。消せないときはサイトを削除せずに 503 `static_remove_failed` を返すので、しばらくしてからやり直す。**削除の成功(204)は「削除の依頼を受け付けてサイトの記録を消した」ことで、配信ファイルそのものは配信を管理する Worker がその依頼を Cloudflare に反映した時点で消える**(通常は数秒。Cloudflare の API が失敗したときは 30 秒・2 分・10 分・以後 1 時間ごとに再試行し、成功するまで最後に配信していた内容が残る)。削除したサイトの設置タグをページに残している場合、配信ファイルが消えると 404 になり、runtime は起動しない(元の表示のまま)。削除の途中で「配信ファイルを作り直す」が押されると、409 `static_remove_conflict` で削除を取りやめる。削除が途中で止まったサイトには、画面に「このサイトの削除が途中で止まっています」が出る。もう一度削除するか、「配信ファイルを作り直す」で配信を戻せる。

## 7. レート制限の実効

2 つのレート制限があり、効き方がまったく違う。

### edge(訪問者のブラウザが直接叩く経路)

`/v1/sites/*`(decision / event)に **IP あたり 20 回 / 10 秒**の Rate Limiting binding を掛けている。**D-lite の `/__ab/*` は binding の対象外**で、こちらの守りは最初からゾーンの WAF に委ねている。

そのうえ Workers の binding 自体が permissive・結果整合で、本番の負荷では実効しなかった実測がある。**実効的な守りはゾーンの WAF Rate Limiting Rule**([デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨))のほうで、`/v1/sites/*` と `/__ab/*` の両方をこれで受ける。

### control(無認証の入口 10 経路)

`auth/google/start`(Google へ送り出す)/ `auth/callback/google`(Google からの戻り)/ `auth/handoff/exchange`(ログイン直後に管理画面がセッションを受け取る使い捨てコードの交換)/ `break-glass/reset-link`(非常用トークンの照合)/ `setup` / 招待受諾 と、非常時だけ開くパスワードの 4 経路(`auth/sign-in/email` / `auth/sign-up/email` / `auth/request-password-reset` / `auth/reset-password`)に、**経路ごとに 10 回 / 10 秒**を掛けている。

`GET /login-options` は無認証で、非常口が開いているかどうかが分かる。守りは sign-in のレート制限と、開いている間の管理画面の帯(と、用が済んだら secret を消す運用)。

**ここが直感に反する**: レート制限のキーになるのは「control に接続してきた側の IP」で、Cloudflare は `CF-Connecting-IP` を実際の接続元で上書きする。管理画面からの操作は「ブラウザ → admin の BFF → control」と流れるので、control から見た接続元は **admin Worker からの接続元 IP**(Cloudflare 内部の固定の値。実測では `2a06:98c0:3600::103` で、操作した人の IP とは無関係)である。つまり **管理画面経由の無認証 POST は、経路ごとに全ユーザーが 1 枠を共有する**。誰かがログインの枠を使い切ると、他の全員のログインも 429 になる(経路は分かれているので、ログイン失敗が招待受諾やリセットを巻き込むことはない)。管理画面は公開されているので、第三者がログインを叩き続けるだけで管理者全員のログインが止まりうる。到達を絞るには管理画面を自分のドメインに載せ、WAF か Cloudflare Access を掛ける([デプロイガイド 4.2・4.5](deploy.md#4-admin-のデプロイ))。逆に、ユーザーごと・攻撃者ごとのブルートフォース制限としては効かない。

control を**直接**叩く経路(API キーを使うエージェント、curl、非ブラウザクライアント)はクライアントの実 IP でキーが分かれるので、IP 単位の制限が意図どおり効く。

**運用者にとっての意味**

- 管理者が数人〜十数人なら、手作業で 10 回 / 10 秒にはまずぶつからない。ぶつかるのは自動化された連続ログイン。CI や運用スクリプトから繰り返しログインする場合は枠を数える
- ログインのブルートフォース対策を本気で掛けたいなら、ゾーン側の WAF か Cloudflare Access を前段に置く([デプロイガイド 7 節](deploy.md#7-無認証入口の防御))
- limiter 自体が壊れたときは、edge / control とも **fail-open**(通してログに残す)

### 429 が訪問者に与える影響

**decision が 429 を受けた runtime は再試行せず、元の表示に倒れる**。サイトは壊れないが、エクスペリエンスは適用されず Exposure も出ない。目標は `dataLayer` への `ab_conversion` push は行われ GA4 には届き、落ちるのは `needsProfile` のサイトの `/event` 転送(Profile の `converted` 履歴)だけ。`needsProfile: false` のサイトは `/v1/*` を呼ばないので影響しない。エラーは訪問者には見えない。したがって WAF のしきい値を絞りすぎると、**特定の送信元(たとえば NAT 配下の 1 つの会社)の露出(と履歴)だけが黙って欠ける**という計測の偏りが生じる。しきい値の決め方は [デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨)。

## 8. 既知の制約

仕様として受け入れている制約。回避策があるものは併記する。

- **SPA の `pushState` では再評価しない。** URL だけが変わって新しいコンテンツが挿入される画面遷移は検知しない。新しい評価はフルリロードを跨ぐ遷移でだけ走る
- **React・Vue 等が管理する要素は、フレームワークの再レンダリングで書き換えが戻ることがある。** `MutationObserver` で再適用を試みるが、仮想 DOM の差分がそれより高頻度・高優先度で走るケースでは打ち勝てない
- **CUSTOM_JS と HTML 内の `<script>` はページ読込ごとに 1 回だけ実行される。** SPA の再描画で要素が作り直されても、再適用されるのは HTML の DOM 挿入だけで、`<script>` は不活性のまま挿入される。CUSTOM_JS は再実行されない。consent の撤回 → 再許可でも再実行されない
- **CSS の変更は prehide(チラつき防止)の対象外。** `<style>` は decision の後に注入されるため、CSS だけで見た目を変えるエクスペリエンスはチラつく可能性がある。Exposure は対照群・処理群とも起動直後に出る(片側だけ発火する SRM を防ぐため)
- **Trusted Types(`require-trusted-types-for 'script'`)を強制するサイトでは HTML / CUSTOM_JS が動かない。** CSP の nonce は引き継ぐが、Trusted Types のポリシーは提供しない。失敗はその変更だけに隔離され、同じパターンの他の変更は動く
- **適用済みの変更は、consent の撤回で元に戻さない。** HTML 挿入 / CSS / CUSTOM_JS は原理的に巻き戻せないため。撤回後の最初のフルリロードから適用されなくなる
- **サイトを削除しても Visitor Profile は即時には消えない。** Durable Object は列挙できないため、`retentionDays` の alarm で自然に消えるのを待つ
- **エクスペリエンス / 目標を削除しても、Profile 内の割当と目標の達成回数は retention まで残る**(掃除されるのは閲覧したページの条件の記録だけ。どの公開中の配信条件からも使われなくなったページの条件は、公開中の設定がまだ Profile を使う(`needsProfile: true`。履歴条件か `persistAssignment` が残っている)ときに限り、次の公開の後の最初のアクセスで消える。Profile を使わなくなった設定では Profile に触れないので、`retentionDays` まで残る)
- **画面の幅の条件は、ページを開いた時点の幅で判定する。** 表示中に窓の幅を変えても判定し直さない。GA4 の端末の区分(User-Agent から決まる)とは定義が違うので、GA4 の `desktop` / `mobile` と件数は一致しない。タグを viewport の meta より前に置いたページ、viewport の meta が無いページでは幅が不明になり、画面の幅の条件を使うエクスペリエンスは配信されない([サイト導入ガイド 3 節](site-install.md#3-タグを置く))
- **「初回の訪問からの経過」は、訪問者 ID を発行した時点から数える。** Cookie の削除やブラウザの保存期限で ID が作り直されると数え直しになる。同意が必要なサイトでは、同意した後の最初の訪問が初回になる。発行時刻を持たない形式の ID(UUIDv7 形式でない、古い版で発行された ID)は「古い訪問者」として扱う(「N 日以上経過」の条件には当てはまり、「N 日未満」の条件には当てはまらない)
- **曜日・時間帯の条件はサイトのタイムゾーン**(サイトの設定。既定 `Asia/Tokyo`)で判定する。訪問者の端末のタイムゾーンではない
- **設置タグのファイルの更新は、Durable Object の CPU 時間の上限を厳密に適用されると止まるおそれがある。** 現在は Free でも更新できているが、Cloudflare が上限を厳密に適用し始めたときは、公開は成功して配信ファイルの更新だけが止まる(公開の結果の `staticDeploy` が `pending`。サイトの上部の警告で気付ける)
- **配信するタグ(runtime と設定)が大きいと、公開の結果に警告が出る。** 警告は公開を止めない。初めて訪れたときの読み込みで、通信の往復が 1 回増えることがある。配信中のエクスペリエンスや変更を減らすと小さくなる

## 9. 既知の課題

- **HTML の変更の html を空のまま保存すると、管理画面にはどのパターン / 変更が原因かが出ない。** control の 422(`invalid_change`、`path: ["payload","html"]`)が表示されるだけなので、空の HTML の変更を探して中身を入れるか削除する

## 10. トラブルシュート

| 症状 | 確認する場所 | 対処 |
|---|---|---|
| **エクスペリエンスが出ない** | エクスペリエンスの URL 条件(配信条件)の一致方式(`equals` は完全一致 — 末尾スラッシュやクエリ文字列で外れる)/ `trafficPercentage` / consent が `denied` になっていないか(Console で `dataLayer`)/ ブラウザが古い設置タグのファイルをキャッシュしていないか / サイトの上部に配信ファイルの警告が出ていないか / 状態が 配信中(`running`)でも未公開でないか | URL 条件の一致方式を `contains` / `startsWith` に緩める。公開の反映は 1 分ほど([4 節](#4-公開の反映))。`reason` を機械的に見るなら [エージェント向けガイド レシピ 4](agent-guide.md#レシピ-4-配信条件の-what-ifなぜこの-url-で出ないのか) |
| **正本 Cookie(`_ab_vid`)が無い** | サイトの `consentMode`(`required` なら同意前は ID を作らない)/ 設置タグの前に `__ab` で同意を渡しているか / Mode C なら参照元の Cookie が存在するか | consent の配線を確認する([サイト導入ガイド 7 節](site-install.md#7-consent-の配線cmp-を使うサイト))。D-lite は HttpOnly なので `document.cookie` には出ない — DevTools の Application → Cookies で見る |
| **`ab_exposure` が GA4 に無い** | `dataLayer` には入っているか(入っていれば GTM 側の問題)/ GTM のカスタムイベントトリガーと GA4 イベントタグ / GA4 のカスタム定義の登録 / DebugView / テストを headless ブラウザで行っていないか(`HeadlessChrome` UA は GA4 のボット除外で落ちる。[分析ガイド 8 節](analytics.md#8-よくある詰まり)) | `dataLayer` に無ければ配信側([5 節](#5-開始直後のチェック))、あれば GTM 側。GTM プレビューで発火を追う([サイト導入ガイド 5 節](site-install.md#5-設置後の確認)) |
| **公開したのに設置タグのファイルが古い** | サイトの上部の警告(「設置タグの配信ファイルが最新の公開内容になっていません」)/ 公開の結果の `staticDeploy`(`pending`)/ デプロイ専用の Worker の secret と Account ID(デプロイガイド 2.9) | 自動の再試行を待つ。続くときは「配信ファイルを作り直す」を押す([4 節](#4-公開の反映))。作り直しても `pending` なら、デプロイ専用の Worker のトークン(Workers Scripts の Edit)が有効かを確かめる |
| **429 が返る** | WAF Rate Limiting Rule のしきい値 / 送信元が NAT で多人数に共有されていないか / 本文が `error code: 1015`(Cloudflare の遮断)か平文の `rate limited`(Worker の binding)か | しきい値を実訪問者数に合わせて上げる。自社オフィスなど既知の送信元は除外する([デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨)) |
| **CSP 違反でコードの変更が動かない** | Console の違反メッセージ / 設置タグに nonce が付いているか / `script-src` が allowlist 方式か / `require-trusted-types-for 'script'` があるか | nonce 方式なら追加設定なしで動く。allowlist 方式は CSP 側の対応が要る。Trusted Types 強制は非対応([サイト導入ガイド 10 節](site-install.md#10-コードの変更と-csp)) |
| **公開が失敗する** | サイトの「公開履歴」の該当行の `error`(失敗コード。管理者以上には生の例外テキストも付く)/ edge・デプロイ専用の Worker・control のデプロイ順 | メッセージのコードで原因を切り分け、再度公開する。旧 version が配信され続けているのでサイトは壊れていない。新機能を使う config は **edge とデプロイ専用の Worker を先にデプロイ**してから公開する([デプロイガイド 6 節](deploy.md#6-更新リリースタグ単位)) |
| **保存すると「メンテナンス中のため、変更を保存できません」になる** | 管理画面の上部の「メンテナンス中」の帯(理由と再開の見込み) | 書き込みの凍結中です([6 節の「メンテナンス中」](#メンテナンス中書き込みの凍結))。作業者が外すまで待つ。作業者の側の確認と外し方は[デプロイガイド 6.6](deploy.md#66-書き込みの凍結メンテナンス中) |

## 11. 使用状況(Cloudflare の上限)

Cloudflare の Free プランには日次の上限があり(アカウント単位、毎日 UTC 0 時 = 日本時間 9 時に戻る)、尽きると翌日まで止まるものがあります。止まる前に気付くための見方が 2 つあります。

| 見方 | 手間 | 上限が尽きたとき | 要るもの |
|---|---|---|---|
| **ツール経由**(ホームの「使用状況」・ユーザーメニュー →「設定」→「Cloudflare 使用状況」・`GET /usage`) | 簡単。判定と上限到達の見込みまで出る | Workers の上限が尽きると control も止まり、**見られなくなる** | 導入時に作るトークン(Account Analytics: Read)を control に入れておく |
| **Cloudflare を直接見る**(GraphQL Analytics API) | クエリを自分で投げ、上限と比べる | ツールの稼働に関係なく見られる(api.cloudflare.com は自分のアカウントの Workers の上限に数えられない) | 別の API トークン(Account Analytics: Read のみ)。control に入れたトークンは読み出せないので使い回さない |

### 設定(システム管理者)

ユーザーメニュー →「設定」→「Cloudflare 使用状況」で変えられます。

- **見られる人**: すべてのメンバー(既定。ホームに要約が出る)/ システム管理者のみ。全員に見せても、出るのはアカウント全体の合計と本製品の内訳だけで、同じアカウントの他のプロジェクトの名前は出ません。顧客ごとにワークスペースを分けている導入では「システム管理者のみ」にできます
- **Cloudflare のプラン**: Free(既定)/ Paid。自動では判定しません(請求の権限を求めないため)。実際は Free なのに Paid を選ぶと、止まる前の警告が出なくなります
- **月額 $5 に含まれる量と比べる**(Paid のときだけ): 月額 $5 のプランに含まれる量(日次の資源は 30 日で割った 1 日分)と比べて表示するか。超えても止まらず、月の合計が含まれる量を超えた分が課金されます。1 日の分を超えても、月の合計が含まれる量に収まれば追加料金はかかりません。API(`GET /usage` の `reference`)は表示の設定に関わらずこの量を返します

### 判定

- Free: 日次の上限に対して 70% 未満「余裕あり」(`ok`)・70% 以上「注意」(`warning`)・90% 以上「危険」(`critical`)・100% 以上「上限に到達」(`exhausted`)。今日の消費のペースが続いた場合に上限に達する時刻も出します(UTC 0 時から 1 時間未満と、次のリセットより後になる場合は出しません)
- Paid: 日次の資源は判定しません(止まらないため)。月額 $5 に含まれる量と比べた結果だけを `within_reference` / `over_reference` で返します。保存量は D1 の 1 データベースあたり 10 GB だけを判定します。Durable Objects の 1 オブジェクトの上限(10 GB)など、オブジェクトごとの上限は判定しません
- D1 の 1 データベースの上限は、本製品のデータベース(`AB_USAGE_RESOURCES` に書いたもの)で判定します。書いていない、または書いた ID がどのデータベースとも一致しない場合は判定しません(「判定していません」と表示)
- 上限の値(2026-10-05 確認、[Workers の料金](https://developers.cloudflare.com/workers/platform/pricing/)・[Workers の上限](https://developers.cloudflare.com/workers/platform/limits/)・[D1 の上限](https://developers.cloudflare.com/d1/platform/limits/)):

| 資源 | Free の日次上限 | Paid の月の込み量 |
|---|---|---|
| Workers のリクエスト | 100,000 | 10,000,000 |
| Durable Objects のリクエスト | 100,000 | 1,000,000 |
| Durable Objects の行の読み取り / 書き込み | 5,000,000 / 100,000 | 250 億 / 50,000,000 |
| D1 の行の読み取り / 書き込み | 5,000,000 / 100,000 | 250 億 / 50,000,000 |
| KV の読み取り / 書き込み・削除・一覧 | 100,000 / 各 1,000 | 10,000,000 / 各 1,000,000 |
| 保存量 | D1 合計 5 GB・1 データベース 500 MB・Durable Objects 5 GB・KV 1 GB | 込み量 D1 5 GB・Durable Objects 5 GB・KV 1 GB(D1 の 1 データベースの上限 10 GB) |

### 上限が尽きたとき(Free)

| 尽きた資源 | 止まるもの | 動き続けるもの |
|---|---|---|
| Workers のリクエスト | 管理画面・control の API(Cloudflare の 1027 のエラーページ)・edge の判定とイベントの送信(`/v1/*`)・D-lite(`/__ab/*`)・配信ファイルの更新(デプロイ専用の Worker) | 設置タグのファイル(静的アセットで、Worker のリクエストに数えられない)・サイトの元の表示(どの場合も) |
| Durable Objects(リクエスト・行の読み書き) | `needsProfile` のサイトの判定(訪問者には元の表示) | 管理画面・ほかのサイトの配信 |
| D1 の行の読み取り・書き込み | control と管理画面のすべて(閲覧・ログイン・API キーの認証・使用状況の表示を含む。D1 のクエリが失敗する) | edge の配信(D1 を使わない)・サイトの元の表示 |
| KV の書き込み(1,000 / 日) | 公開(配る設定の書き込み) | 配信中の設定・管理画面での保存 |

訪問者のブラウザには、失敗したリクエストのたびに Console に `Failed to load resource …` が 1 行ずつ出ます。対象は `/v1/*`・`/__ab/*` を使うサイトの判定と送信です。表示は元のまま壊れません。使用状況が開けないときは、上の「Cloudflare を直接見る」手順で確かめます。edge の Route は「上限超過時に Worker を通さずオリジンへ流す」設定(fail open)にしない運用を前提にしています(オリジンの応答はサイトごとに違い、訪問者の ID を含む送信がオリジンに届くため)。

### Cloudflare を直接見るクエリの例

`deploy.md` 9 節 (b) と同じ方法で、Account Analytics: Read のトークンを使います。

```bash
curl -s https://api.cloudflare.com/client/v4/graphql -H "Authorization: Bearer $CF_ANALYTICS_TOKEN" -H 'content-type: application/json' \
  -d '{"query":"{ viewer { accounts(filter: { accountTag: \"<アカウント ID>\" }) { workersInvocationsAdaptive(limit: 100, filter: { date_geq: \"<今日 UTC>\", date_leq: \"<今日 UTC>\" }) { dimensions { scriptName } sum { requests } } durableObjectsPeriodicGroups(limit: 100, filter: { date_geq: \"<今日 UTC>\", date_leq: \"<今日 UTC>\" }) { sum { rowsRead rowsWritten } } } } }"}'
```

`workersInvocationsAdaptive` の `requests` の合計を Workers の日次上限と、`durableObjectsPeriodicGroups` の `rowsWritten` を Durable Objects の行の書き込みの上限と比べます。
