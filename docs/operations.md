# 運用ガイド

エクスペリエンスを作り、本番に出し、様子を見るための手引き。デプロイ済みの環境([デプロイガイド](deploy.md))と、設置済みのサイト([サイト導入ガイド](site-install.md))があることが前提。

## 1. 用語の要約

画面の表記と、API・`CONTEXT.md` の英語の識別子の対応。運用で毎日使うものだけ。

| 画面の表記 | 英語の識別子(API・コード) | 1 行の定義 |
|---|---|---|
| **ワークスペース** | workspace | ユーザーとサイトを束ねる単位。メンバーはここで 1 つのロールを持つ |
| **サイト** | site(ID = サイト ID) | エクスペリエンスを配信する対象のサイト。導入の形(Deployment Mode)・同意の扱い(`consentMode`)・保存期間などの設定を持つ |
| **サイト設定** | `/w/:wid/sites/:sid/settings`(管理画面の URL)・`PATCH /sites/:sid` | サイトごとの設定。サイトの画面で左メニューの下の「設定」を開くと、見出し「サイト設定」の下に一般・ドメイン(導入の形とタグを置くドメインの一覧)・導入タグ・訪問者 ID・外部計測の名前・外部 ID・危険な操作(オーナーだけ)が並ぶ |
| **エクスペリエンス** | experiment | サイトに出す変更のまとまり。種別(テスト / パーソナライズ)を持つ。対象 URL・配信条件・パターンを持ち、状態は 下書き / 配信中 / 一時停止 / 終了(`draft` / `running` / `paused` / `archived`) |
| **テスト / パーソナライズ** | `kind`(`test` / `single`) | エクスペリエンスの種別。テストは 2 つ以上のパターンに振り分けて比べる。パーソナライズはパターン 1 つ・重み 100 で、条件に合う訪問者全員(配信率の範囲)に表示する(振り分けない)。作成後は変えられない |
| **パターン** | variant | エクスペリエンスの中の 1 案(A パターン・B パターン)。重み(配分)と変更の集合を持つ |
| **オリジナル** | `original` | 変更を持たず、元のページをそのまま表示するパターン。テストだけで使える。作成したテストの A パターンはオリジナル |
| **メモ** | `description` | エクスペリエンスとパターンに付ける社内用の欄(1,000 字まで)。外部には出力されない。状態にかかわらず編集でき、変えても「未公開の編集あり」にならない。オーディエンスの「メモ」は 1 行(500 字まで) |
| **変更** | change | ページへの 1 つの書き換え(`TEXT` / `IMAGE` / `HIDE` / `ATTRIBUTE` / `HTML` / `CSS` / `CUSTOM_JS`)。後ろ 3 つを**コードの変更**と呼ぶ |
| **目標** | goal | コンバージョンの定義(`PAGEVIEW` / `CLICK` / `CUSTOM`) |
| **オーディエンス** | audience | 名前を付けた訪問者の条件。サイトごとに作り、エクスペリエンスの配信条件で選ぶ。編集は次の公開で、参照するすべてのエクスペリエンスに反映される |
| **公開** | publish | **サイト単位**の本番反映。そのサイトの配信中のエクスペリエンスすべてを 1 つの設定にまとめて配信に載せる |
| **開始 / 一時停止 / 再開 / 終了** | status を `running` / `paused` / `running` / `archived` に | 状態の変更。成功するとサイトを自動で公開する。終了は元に戻せない |
| **未公開の編集あり** | `unpublished` / `hasUnpublishedChanges` | 下書きに、まだ公開していない編集がある |
| **外部計測(dataLayer 出力)** | analytics | dataLayer に送る値(GA4 などの外部の計測で使う)。エクスペリエンス・パターン・目標の名前の指定と追加の値、サイトの「外部計測の名前」の名札。名前を指定しなければ ID を送る。管理画面では「基本設定」の下・パターンの詳細・目標の編集のカードで入力し、「出力される内容」に送る値が出る |
| **基本設定** | `overview`(エクスペリエンスの編集のタブ) | 「基本」のカード(名前・メモ)、「配信条件」のカード(① どのページで = 対象 URL、② どの訪問者に = 訪問者の条件、③ そのうち何 % に = 配信率と割当の固定)と、エクスペリエンスの外部計測。もう 1 つのタブが「パターン」 |
| **割当の固定** | `persistAssignment` | 初回の割当を訪問者ごとに保存し、配分を変えても再割当しない |
| **訪問者 ID** | identity(`idSource`) | 訪問者を見分ける ID の取り方(サイト設定の「訪問者 ID」) |
| **導入の形**(Mode A: JS Cookie / Mode B: サーバー発行 Cookie / Mode C: BYOID) | `mode`(`A` / `B`)と `idSource`。Mode B は旧称 D-lite(導入の入力ファイルの `dlite_hosts`) | 訪問者 ID の Cookie を誰が書くか。A はタグが JavaScript で書き、B はサイトと同じゾーンの Workers Route(`/__ab/*`)から edge が `Set-Cookie` で発行する(Safari の 7 日の制限を受けない。`サブドメインをまたいだ共有` がオフなら HttpOnly)。C はサイトの既存の Cookie を使う |
| **サブドメインをまたいだ共有** | `shareSubdomains`(既定 on) | 訪問者 ID の Cookie を、登録ドメイン(サブドメインを付けないドメイン)の下のどのホストでも読めるように発行する。オンなら Mode B の Cookie は HttpOnly にならず、同じ登録ドメインのすべてのホストを信頼することになる([サイト導入ガイド 8 節](site-install.md#サブドメインをまたいで-id-を共有する))。確かめ方は[10 節](#10-トラブルシュート) |
| **オーナー / 管理者 / 編集者 / 閲覧者** | `owner` / `admin` / `editor` / `viewer` | ワークスペースでのロール |
| **システム管理者** | instance admin | この導入全体の管理者。すべてのワークスペースのオーナーを兼ねる |
| **API キー** | API key | エージェント・スクリプト用の鍵。**範囲**(すべてのワークスペース = `full` / 1 つのワークスペース = `workspace`)と**権限**(`roleCap`)を持つ |
| **操作の記録** | `audit-events`(API のパス)・`audit_events`(表) | 人とアクセス権の操作と、サイト・エクスペリエンスなどの変更の、1 回ごとの要約。左メニューの下の「設定」の「操作の記録」で見る([6 節](#操作の記録と変更履歴)) |
| **変更履歴**(エクスペリエンスのタブ) | `history`(API のパス) | 1 つのエクスペリエンスの操作の記録。エクスペリエンスの画面の「変更履歴」タブで、メンバー全員が見られる。版ごとの公開内容を書いた文書の「変更履歴」(`CHANGELOG.md`)とは別 |

関係は「ワークスペース ⊃ サイト ⊃ エクスペリエンス ⊃ パターン ⊃ 変更」。目標とオーディエンスはエクスペリエンスではなく**サイト**に属し、複数のエクスペリエンスから参照される。

### 状態(Desired Status)と公開済みの設定は別物

- **状態(Desired Status)** = 管理画面で設定したエクスペリエンスの状態(下書き / 配信中 / 一時停止 / 終了 = `draft` / `running` / `paused` / `archived`)。データベース上の値
- **公開済みの設定(config)** = 最後に成功した公開が配信に載せたもの。訪問者に実際に届いているのはこちらだけ

この 2 つがずれることがある。ずれ方は 2 通り。

- **開始・一時停止・再開・終了は、成功時にサイトを自動で公開する**ので、状態の変更は原則すぐ配信に反映される。自動の公開が失敗したときだけ、状態は 一時停止(`paused`)なのに配信は 配信中(`running`)のまま、といった差が残る(エクスペリエンス一覧の「本番」の列に「未反映」と出て、ポイントすると「配信中: 配信中(一時停止 は未反映)」のように差が出る。公開で再試行する)
- **変更・パターン・配信条件・目標を編集しただけでは公開されない**。下書きは安全に貯まるだけで、訪問者には届かない。届けるには**公開**を押す(管理者以上)

「管理画面で直したのに本番が変わらない」の大半はこの 2 つ目である。

## 2. エクスペリエンスのライフサイクル

1. **作成**(編集者以上): 対象のワークスペース → サイト → エクスペリエンスを新規作成する。A パターン(ID `a`・オリジナル)と B パターン(ID `b`)が 50:50 で自動生成される(種別がパーソナライズなら A パターン(ID `a`)が重み 100 で 1 つ)
2. **編集**(編集者以上): パターン・変更・配信条件・目標を編集する。**コードの変更を含むあらゆる下書きを編集者が作れる**。保存しても下書きのままで、訪問者には届かない
3. **下書きの確認**([3 節](#3-下書きプレビュー)): 対象ページで実際の見た目と適用結果を見る
4. **開始**(管理者以上): 下書き → 配信中(`draft → running`)。成功すると**サイトが自動的に公開される**。テストでは、開始の前に評価計画のタブで判定に使う目標などを決める(結果を記録するサイトでは、判定に使う目標が無いと開始できない。[12 節](#12-テストの結果の記録))。開始した後のテストは、変えられる設定が限られる([12 節](#開始後のテストの編集))
5. **一時停止 / 再開**(管理者以上): 配信中 ↔ 一時停止(`running ↔ paused`)。これも自動の公開を伴う
6. **終了**(管理者以上): 配信中・一時停止 → 終了(`running | paused → archived`)。**元に戻せない**。同じ内容でやり直すときは複製して新しいエクスペリエンスを作る。テストは終了のときに採用したパターン(なしも可)を記録でき、終了したテストはメモ以外を編集できない([12 節](#終了と採用))

**ID は作成後に変更できない**(エクスペリエンス / パターン / 目標 / オーディエンス)。とくに `experimentId` は割当ハッシュの入力なので、作り直すと全訪問者の割当が変わる。

**一度開始したエクスペリエンスの ID は、削除した後もそのサイトでは使い直せない**(作成・複製で同じ ID を指定すると 409 `id_taken`)。訪問者に保存された割当(`persistAssignment` と Visitor Profile)は保存期間まで残り、同じ ID の新しいエクスペリエンスに古い割当が適用されてしまうため。結果を記録するかどうかや、種別(テスト / パーソナライズ)に関係なく同じ。開始していない下書きを削除した場合は、同じ ID をまた使える。

**エクスペリエンスを削除できるのは、下書きと終了したものだけ**(編集者以上)。終了にしても、終了の公開が失敗して、まだ配信中か一時停止のまま公開されている間は削除できない(409 `experiment_active`)。もう一度公開して終了を配り終えてから削除する。

### パターンの編集

エクスペリエンスの編集画面の「パターン」のタブで、左の一覧からパターンを選び、右で設定・変更・外部計測を編集する。パターンの追加・削除・名前・重み・オリジナルの切り替え・外部計測は、下書きのときだけ変えられる(開始後は変えられない)。

- **ID**: 「パターンを追加」で、使われていない最初の文字(`a`, `b`, `c` …、`z` の次は `aa`)が自動で付く
- **オリジナル / 変更あり**: パターンの設定で選ぶ。オリジナルは変更を持てないので、変更のあるパターンをオリジナルに切り替えると、保存のときにそのパターンの変更を削除する(保存の前に「変更あり」に戻せば変更も戻る)。パーソナライズでは選べない
- **重みの入力**: 一覧の各行の欄に % で入れる。一覧の下に合計が出て、100 でなければ赤くなり保存できない。「均等に配分」を押すと 100 をパターンの数で割り、割り切れない分は一覧の上から 1 ずつ足す(3 つなら 34 / 33 / 33)。均等に配分したままパターンを追加・削除すると、自動で均等に配り直す(「均等に配り直しました」と出る)。手で配分を変えた後に追加したパターンは 0% になる
- **0% のパターン**: 重み 0% は保存できるが、誰にも表示されない。一覧に「0% = 誰にも表示されません」と出て、下書きを開始するときの確認にも「<名前> は重み 0% のため、誰にも表示されません」が並ぶ(再開のときは出ない)
- **メモ**: パターンの設定とエクスペリエンスの「基本設定」にある「メモ(社内用。外部には出力されません)」の欄。状態にかかわらず編集できる(終了したエクスペリエンスでもメモだけは直せる。閲覧者は編集できない)。メモだけを保存しても「未公開の編集あり」にならない
- **名前と外部計測**: 「名前」の欄は管理画面の中だけで使い、訪問者には届かない。dataLayer の `ab_variant_name` などには、外部計測(dataLayer 出力)の「パターン名」などで指定した値、指定が無ければ ID を送る([サイト導入ガイド 12 節](site-install.md#サイト単位エクスペリエンス単位の名前))。外部計測の欄に入れた値は訪問者もブラウザで見られるので、社内向けの言葉や個人情報は入れない
- **目標名**: 目標の編集の外部計測で指定する。状態にかかわらず変えられ、変えて公開した時点から `ab_goal_name` の値が変わる。集計は `ab_goal_id` で行う([分析ガイド 1 節](analytics.md#1-何が測れるか))

### 未公開の編集の見え方

最後に成功した公開以降に編集があると、管理画面が 3 か所で知らせる。

- **エクスペリエンス一覧**: そのエクスペリエンスに「未公開の編集あり」バッジ
- **上部バー**(サイトの中のどの画面にも出る): 「未公開の編集あり」の表示と、強調された「公開」ボタン(目標・オーディエンス・タイムゾーンの変更はサイト単位で検知する)。上部バーには版の表示(「配信中 vN」。一度も公開していなければ「未公開」)もあり、押すと直近 5 回の公開が開き、「すべての公開履歴」から公開履歴の画面へ移る
- **公開の確認画面**(上部バーの「公開」を押すと開く): 前回の公開以降に変わったエクスペリエンス / 変更の一覧(誰が・いつ・「コードを含む」「外部の URL を含む」の印)。コードの印は、HTML / CSS / CUSTOM_JS に加えて `<style>` などに当たる可能性のある TEXT / ATTRIBUTE と、rel の変更にも付く。保存と公開が重なり、更新時刻だけでは見つからなかった変更も、公開中の設定との比較で一覧に補う。公開する前にここを読む

一度編集して元に戻しただけでも「未公開の編集あり」と出る。公開の確認画面では設定の比較も行うが、エクスペリエンス一覧と上部バーの未公開の表示は更新時刻による判定を保つ。メモの変更だけは出ない(公開しても配信の中身が変わらないため)。

### 公開はサイト単位

公開は、そのサイトの**配信中のエクスペリエンスすべて**を 1 つの設定にまとめる。したがって「エクスペリエンス X の修正だけを出す」ことはできず、公開した時点で**ほかのエクスペリエンスの未公開の編集も一緒に出る**。複数人で使うサイトでは、公開の確認画面の変更サマリを毎回読む。管理画面は確認画面で見た内容のときだけ公開する。確認の後に保存内容が変われば、確認画面を読み直して確かめ直す。開始・一時停止・再開・終了でも、ほかの未公開の変更を一覧してから、確認した内容に固定してサイト全体を公開する。

公開は失敗しても前の版が配信され続ける(配信の切り替え(activation)の前に失敗するため)。失敗した回は公開履歴(上部バーの版の表示から開く)に `failed` として残る。

### オーディエンスと配信条件

**オーディエンスの作り方**: サイトの「オーディエンス」→「新しいオーディエンス」を開き、左の部品をドラッグして条件を組み立てる(部品をクリックすると一番外側のグループに入る)。グループは「すべて満たす / いずれかを満たす」と「除外する」を選べる。入れ子は一番外側のグループの中に 4 段まで。配信条件で参照したオーディエンスは、公開のときに参照のたびに中身を展開する。サイト全体で「オーディエンスの条件の数 × 参照の数」の合計は 20,000 まで(超えると公開が止まる)。既存のオーディエンスを取り込むと、その時点の定義のコピーが入る(元のオーディエンスを後から変えても連動しない)。

**対象 URL**(基本設定のタブの「配信条件」のカードの「① どのページで」): エクスペリエンスを動かすページを、「含める」と「除く」の 2 つの枠に行を並べて書く。含めるの行のどれかに一致し、除くの行のどれにも一致しないページが対象。各行は、最初の条件(パス / ホスト / URL のページの一致)に、「+ 条件(かつ)」でほかのページの一致(パス / ホスト / URL)と URL のパラメータの条件(値が一致・値を含む・パラメータがある)を「かつ」で足せる。行の条件をすべて満たすと、その行に一致する。ホストとパスを組み合わせて絞るとき(「ホストが X で、かつパスが正規表現に一致する」など)は、同じ行に並べる(別の行にすると「または」になる)。1 つの行の中は、最初の条件 → ページの一致 → パラメータの条件の順に並ぶ。上限は含める 1〜10 行・除く 0〜10 行・1 行の「かつ」のページの一致 5 個・1 行のパラメータ 5 個。各条件の × はその条件だけを消し、行ごと消すときは「この行を消す」を押す。最初の条件の × を押すと、次のページの一致が最初の条件に繰り上がる(ページの一致がほかに無ければ値が空になる。空のままでは保存できない)。同じ名前のパラメータが URL に複数あれば、どれか 1 つの値が条件を満たせば一致する。「パラメータが無い」ページだけにしたいときは、除くの行に「パラメータがある」を書く。判定できない除くの行(パスが 256 字を超えるページでのパスの正規表現など)があるページは対象外になる。ページの URL・ホスト・パス・パラメータの条件は対象 URL だけに書く(配信条件とオーディエンスには無い)。プリハイド(変える要素を判定の前に隠す)も対象 URL に一致したページだけで行う

**エクスペリエンスの配信条件**(「② どの訪問者に」): 1 段の「すべて満たす / いずれかを満たす」に条件の行を並べる。行の種類に「オーディエンス」があり、入れ子や除外が要る条件はオーディエンスで作って選ぶ。条件が無ければ、対象 URL のページを開いた全員が対象。

**更新の前に保存したページの条件**: 配信条件・オーディエンスに、更新の前に保存したページの URL・ホスト・パス・パラメータの条件が残っていると、その行が警告の色で出て、保存と、エクスペリエンスの開始・再開ができない。条件の内容を対象 URL に書き、「この条件を消す」で消してから保存する。古い条件が、更新の前の対象 URL と組み合わせて(「すべて満たす」で)使われていたときは、新しい行を足さずに、その対象 URL の行と同じ行に入れる(パラメータの条件も、ホスト・パス・URL の条件も、その行の「+ 条件(かつ)」で足す)。別の行に足すと「または」になり、配信先が広がる。オーディエンスに残った条件は、オーディエンスから消し、そのオーディエンスを使うエクスペリエンスごとに対象 URL に書く。更新のときに配信中だったこうしたエクスペリエンスは、更新で一時停止になっている(操作の記録と変更履歴に、ログイン方法が「定期処理」の状態の変更の行で残る)。直して再開すると、テストなら結果に「テスト中の変更」が 1 件記録される(判定は止まらない)。配信条件と対象 URL を「いずれかを満たす」でまたぐ形(「/lp/ のページ、またはスマートフォンの訪問者」など)は書けないので、エクスペリエンスを分ける。

**閲覧したページの条件**: URL / パス / ホストを直接書く。同じ一致の仕方(部分と演算子と値)なら、回数や期間を変えても閲覧回数は共有される。一致の仕方を変えると別のページの条件になり、閲覧回数は数え直しになる。

**期間の条件**: 閲覧・目標の「最後の閲覧・達成が N 日以内」「過去 N 日に閲覧していない」の N は、訪問者データの保存期間(`retentionDays`)以下にする。保存期間を短くするときは、先に条件の期間を直して公開する(期間が保存期間を超える条件が残っていると、保存期間の変更は 422 で止まる)。

**編集と公開**:

- 配信中のエクスペリエンスが使っているオーディエンスを保存しようとすると確認が出る。編集は次の公開で、参照するすべてのエクスペリエンスに反映される
- 公開の確認画面に「オーディエンスの変更」(配信対象が変わるエクスペリエンス)・次の公開で数えるのをやめるページの条件・画面の幅の条件についての注意・公開で止まる理由が出る
- 配信条件から参照されているオーディエンスと、オーディエンスから参照されている目標は削除できない

**アクセシビリティ設定**: 左メニューの下の「設定」→「画面表示」の「ドラッグの代わりにボタンで操作する」をオンにすると、「ここに追加」・↑↓・「移動先」で条件を並べ替えたり、グループの間で動かしたりできる(設定はこのブラウザだけに保存される)。オフのときは、オーディエンスの作成と配信条件の画面の条件の下に、この設定への案内が出る。

#### 配信条件の正規表現

管理画面の正規表現の入力欄の案内が、この節を参照する。

- 正規表現を書けるのは、対象 URL の行・閲覧したページの条件・目標の PAGEVIEW のページの一致
- 使えるのは**パスとホストだけ**。URL 全体には使えない(パスの正規表現で書き換える)
- **部分一致**。全体に一致させるときは `^` と `$` を付ける
- 使える書き方:

| 書き方 | 意味 |
|---|---|
| ふつうの ASCII 文字 | その文字 |
| `\.` `\/` `\-` `\?` `\*` `\+` `\(` `\)` `\[` `\]` `\{` `\}` `\^` `\$` `\\` と、`\` に縦線を続けた形 | 記号そのもの |
| `.` | 任意の 1 文字 |
| `[...]` / `[^...]` | 文字クラス / その否定 |
| `\d` `\w` `\s` | 数字 / 英数字と `_` / 空白 |
| `^` `$` | 先頭 / 末尾 |
| `( )` `(?: )` と縦線 | グループ / 選択 |
| `?` `*` `+` `{n}` `{n,m}` | 繰り返し(`m` は 100 まで。0 回だけの `{0}` `{0,0}` は使えない) |

- 使えないもの: 後方参照、先読み・後読み、名前付きグループ、フラグ、上限のない `{n,}`、最短一致(`*?` など)
- 上限: 式は 200 字まで、1 つの正規表現は 200 命令(変換後の大きさ。`{n,m}` は展開して数える)まで、1 つのエクスペリエンスの対象 URL の全部の行で 500 命令まで(超えると保存できない)、サイト全体で 500 命令まで(超えると公開が止まる)。数え方は次のとおり
  - 対象 URL の正規表現は、行ごとに数える(エクスペリエンスごとに別々に照合されるため)
  - 閲覧したページの条件の正規表現は、同じ一致の仕方なら何件から使っても 1 つと数える
- 大文字と小文字を**区別する**。ホストは小文字にして照合するので、式のホストも小文字で書く
- `¥`(円記号)と全角の文字は、`\` と半角に置き換えられる。日本語のパスは `%E3%81%82` のようにエンコードした形で書く
- 照合するパスが 256 字を超えるページでは判定しない(そのページでは、対象 URL の含めるの行なら一致しない、除くの行ならそのページは対象外になる)
- 管理画面の「試す」欄に値を入れて、一致するかを確かめられる

### 複製

エクスペリエンスの見出しの「複製」から、どの状態のエクスペリエンスでも下書きを作れる(元は変わらない。編集者以上)。

- **同じ内容でエクスペリエンスを作成**: 種別・すべてのパターンと変更・重み・オリジナルの印・メモ・配信率・割当の固定・対象 URL・配信条件・外部計測の上書きを写す(更新で今の名前から写した外部計測の名前も写るので、古いテストの複製は、複製の後に外部計測を見直す)。開始・終了の時刻と公開の履歴は写さない
- **選んだパターンだけを表示するエクスペリエンスを作成**: 選んだパターンの変更だけを持つパーソナライズを作る。配信率は 100%、割当の固定は off で作る(「勝ったものを全員に出す」ための複製で、元の配信率のままだと出したつもりで一部にしか届かないため)。パーソナライズの元からは「同じ内容」だけ。オリジナルのパターンは選べない(変更を持たないため)
- ID を省略すると `<元の ID>-copy`、`-copy-2` … の空いているものになる。名前は「<元の名前> のコピー」/「<元の名前>(<パターン名> だけを表示)」
- 「同じ内容」が写すのは保存済みの中身。公開していない編集があれば、それも写る。テストの評価計画も初期値として写す(下書きの間は変えられる)
- 「選んだパターンだけを表示」が写す変更は、テストで実際に配信していた中身(終了したテストは終了の直前に配信していたもの)。保存したが公開していない編集は入らない(テストで測った中身だけを全員に出すため)。配信を確かめた記録が無いとき(開始していない下書きなど)は保存済みの中身を写す
- 結果・採用の記録・計画の変更の履歴は写さない

### 重なったときの優先

同じ要素を複数のエクスペリエンスが変えるとき、次の順で後ろのものが優先される: パーソナライズ(作成の古い順)→ テスト(開始・再開の新しい順)。つまり、テストはパーソナライズより優先され、テストどうしは**先に配信に入ったもの**が優先される(後から開始・再開したテストで、配信中のテストのパターンが途中から見えなくなるのを防ぐため)。一時停止したテストを再開すると、その間に開始した同じ要素を変えるテストより優先が低くなる。パーソナライズどうしは後に作成したものが優先される。

- 優先は要素の部分ごとに決まる: 文言(TEXT)・画像の `src`(IMAGE。ATTRIBUTE の `src` と同じ部分)・同じ名前の属性(ATTRIBUTE)・表示 / 非表示(HIDE)・HTML の置き換え(要素のすべての部分)。違う部分(例: 一方が文言、もう一方が非表示)は両方効く
- HTML の挿入(前・後・末尾)は両方入る(並びの順)
- IMAGE は `src` を書いて `srcset` を消すが、優先の対象は `src` だけ。優先の低い ATTRIBUTE の `srcset` が後から一致すると、そちらの画像が表示されることがある(画像を差し替えるときは IMAGE に揃える)
- CSS は、詳細度が同じなら後に入れたもの(優先の高い方)が勝つ。詳細度が違うときは保証しない。カスタム JavaScript は保証しない
- テストのパターンが何も変えない部分(変更の無い基準など)では、優先の低いパーソナライズの変更が見える
- 優先を保証するのは**同じ要素の同じ部分**まで。祖先と子孫にまたがる重なり(優先の低い文言の変更が祖先に効き、優先の高い変更が書いた子孫ごと書き換える、優先の高い HTML の挿入で入った中身に優先の低い変更が効く、など)は保証しない
- ATTRIBUTE の `style` と HIDE(表示 / 非表示)は別の部分として扱う。優先の低い `style` の変更が後から一致すると、優先の高い非表示を上書きすることがある
- 下書きのプレビューも同じ並びの順に適用するので、最初の表示の勝ち負けは本番と同じ。ただし、後から要素が現れた・クラスが付いたなどで後から一致した場合の勝ち負けは、本番と違うことがある

**重なりの警告**: 公開・開始・再開のときに、同じ対象 URL の条件で同じセレクタを変えるエクスペリエンスがあれば、どちらが優先されるかを警告する(公開は止めない)。警告が出るのは、**対象 URL の条件とセレクタの文字列がどちらも完全に一致するとき**だけ(対象 URL は、行とパラメータの並びの違いを無視して比べる)。範囲の違う URL の条件の重なり(サイト全体の「/ で始まる」と特定ページの「/lp と一致」など)や、別のセレクタで同じ要素に当たる場合は警告されない(上の優先の規則でどちらが見えるかは決まる)。

### パーソナライズの配信率

パーソナライズの配信率を 100% 未満にすると、条件に合う訪問者のうちその割合にだけ表示する(段階的に出すための設定)。表示しなかった人は何も送らないので、表示した人と比べて効果を測ることはできない。効果を測るときはテストにする。

### パーソナライズを長く出し続けるとき

- サイトの HTML が変わってセレクタが外れると、変更は気づかないうちに適用されなくなる(エラーは出ない)。定期的に表示を確かめる
- 表示のちらつきを防ぐ一時的な非表示(prehide)は、対象の要素に毎回かかる
- 配信中のエクスペリエンスが増えるほど配る設定が大きくなり、初回の読み込みが遅くなる
- 恒久的な変更は、サイトのコードに入れてパーソナライズを終了するのが基本

## 3. 下書きプレビュー

対象ページを `#__ab_preview=<experimentId>:<variantId>` 付きで開くと、指定したパターンを強制的に見られる(認証不要)。複数指定はカンマ区切り: `#__ab_preview=exp_a:b,exp_b:a`。

**プレビューは完全隔離モード**で、指定したエクスペリエンスだけを適用し、**Cookie・consent・decision 通信・目標・Exposure に一切触れない**。したがって計測に混ざらない代わりに、**Exposure の確認には使えない**([5 節](#5-開始直後のチェック))。

### `AB.getPreviewReport()` の読み方

プレビュー中は Console で `AB.getPreviewReport()` が変更ごとの適用結果を返す(通常表示では常に `null`)。

| フィールド | 見方 |
|---|---|
| `matched` | selector に一致した要素数。**0 なら selector が外れている**(ページ構造が変わった / タイポ / 描画前) |
| `applied` | 適用に成功したか |
| `error` | 適用時の例外メッセージ。**CSP でブロックされた CUSTOM_JS はここに出る** |

エクスペリエンス単位の `error` は 3 種類ある(いずれも `changes: []` で、適用も割当もされない)。

- `unknown experiment or variant`: 指定したエクスペリエンス / パターンが配信 config に無い
- `invalid preview request`: フラグメントの書式が壊れている(`エクスペリエンス ID:パターン ID` になっていない・空)
- `duplicate experiment`: 同じエクスペリエンスを 2 回以上指定した(2 回目以降がこれになる)

**空配列(`[]`)が返るとき**: プレビューの処理が動けば、指定したエクスペリエンスごとに必ず 1 行が入る(ID や書式の誤りも上の `error` 付きの行になる)。空配列は、プレビューの処理がまだ始まっていないか、始められなかったことを表す。設置タグのあるページをこの URL で開くと、タグはプレビューの処理を設置タグと同じオリジンの別ファイル `/s/preview/<hash>.js` から読み、読めなければ何も適用せず元の表示のままにする。次の順に確かめる。

1. **読むのが早すぎないか**: タグは別ファイルを、サイト設定の `decisionTimeoutMs`(300〜3000 ミリ秒)まで待つ。ページの読み込みが終わってからこの時間だけ待ち、もう一度 `AB.getPreviewReport()` を読む
2. **Console のメッセージ**: 読み込めなかったときは `wtt: preview unavailable`、読み込んだ後に処理が例外で止まったときは `wtt: preview failed` が出る。どちらも `console.debug` なので、DevTools の Console でログレベルの Verbose を表示しないと見えない
3. **別ファイルの HTTP ステータス**: DevTools のネットワークの記録で `/s/preview/` への要求を見る。404 なら、設置タグのファイルが指す別ファイルが配信側にもう無い(配信側に残る別ファイルは、ツールの更新のうちプレビューの処理が変わった直近 2 回分だけである。設置タグのファイルがそれより前の更新のまま作り直されていないときに起きる)。サイトを公開し直すか、サイトの上部に配信ファイルの警告が出ていれば「配信ファイルを作り直す」を押す(管理者以上。API は `POST /sites/<siteId>/static/redeploy`)。要求が `(blocked:csp)` と表示されていれば、ページの CSP にブロックされている([サイト導入ガイド 10 節](site-install.md#10-コードの変更と-csp))。200 なのに読み込めないときは、CSP のブロックか、`decisionTimeoutMs` までに読み終わらなかったかのどちらか

curl で別ファイルの URL を確かめる方法と、作り直しの結果の読み方は[エージェント向けガイド レシピ 2](agent-guide.md#レシピ-2-下書きを検証する公開前に本物のページで見る)の末尾にある。どの原因でも、下の「未公開の下書きを本物のページで見る」の方法なら別ファイルを読まずにプレビューできる。

**コードの変更を含むエクスペリエンスは、開始する前にここで `error` が空であることを確認する**。

### 未公開の下書きを本物のページで見る

公開されていない下書きはプレビューだけでは見られない(配信 config に載っていないため)。エージェント面の `GET …/draft-bootstrap` が返す JS をページに注入する([エージェント向けガイド レシピ 2](agent-guide.md#レシピ-2-下書きを検証する公開前に本物のページで見る))。

> **注意**: `draft-bootstrap` が返すのは設置タグのファイルと同形式の**完全に機能する bootstrap** で、隔離されるかどうかは URL に `#__ab_preview=` フラグメントがあるかどうかだけで決まる。**フラグメント無しの URL に注入すると下書きが本番として動く**。未公開のエクスペリエンスが実際に適用され、Cookie が作られ、`ab_exposure` が計測に混ざる(GA4 のデータに下書きの計測が入る)。注入したページは必ず `#__ab_preview=<experimentId>:<variantId>` 付きの URL で開く。

## 4. 公開の反映

公開から訪問者のブラウザに届くまでは **1 分ほど**。内訳は次の 2 つが積み重なる。

| 要素 | 最大 |
|---|---|
| 配信ファイルの更新(デプロイ専用の Worker が設置タグのファイルを作り直す。公開の結果の `staticDeploy` に出る) | 数秒 |
| ブラウザのキャッシュ(`Cache-Control: public, max-age=60`) | 60 秒 |

公開直後に本番を見て「変わっていない」のは、たいていこのブラウザのキャッシュの待ち時間である。反映の確認は次で早い。

```bash
curl -s "https://<設置ホスト>/s/<siteId>.js" | head -c 300
```

先頭のコメント行が `/* AB Test and Target Harness bootstrap (site <siteId>, config v<version>, runtime <ハッシュ>) */` の形で、`v<version>` が公開した版になっていれば反映済み。古い番号のままなら、まだ配信ファイルが更新されていない(下の警告を見る)。

**設置タグのファイルの更新が済んでいないとき**: 公開は成功(`ok: true`)でも、配信ファイルの更新だけが遅れる・失敗することがある(公開の結果の `staticDeploy` が `pending`)。このとき管理画面のサイトの上部に「設置タグの配信ファイルが最新の公開内容になっていません」の警告が出る。デプロイ専用の Worker が失敗を自動で再試行する(30 秒・2 分・10 分、以後 1 時間ごと)ので、たいていは待てば直る。続くときは、管理者以上が警告の「配信ファイルを作り直す」を押す(API は `POST /sites/<siteId>/static/redeploy`)。更新が済むまでは、前に作った配信ファイルが訪問者に届く(初めての公開でまだ無いときは、タグが読み込まれない)。サイト設定(訪問者 ID・外部計測の名札)を保存したときも、配信ファイルを自動で作り直す(公開は不要)。

runtime を新しい版に更新したときも、デプロイ専用の Worker が次の公開か、遅くとも 1 時間以内に全サイトの配信ファイルを作り直す。作り直しの間に前の runtime のファイルが残っても、サイトは動く。

導入全体の配信ファイルの状態(更新待ち・削除を受け付けたがまだ消えていない配信ファイル・最後のエラー・記録の食い違い)は、システム管理者が左メニューの下の「設定」→「配信ファイル」(「システム」の見出しの下)で見られる。配置の失敗が続いている・記録が食い違っているあいだは、システム管理者の画面の上部に帯が出る。使い方は 6 節の「システム管理者」。

**ゾーンの Cache Rule は念のための設定**(必須ではない)。ゾーンの Browser Cache TTL(既定 4 時間のプランがある)が、ゾーンのキャッシュに当たった応答の `Cache-Control` を上書きする場合、戻り訪問者のブラウザが古い設定を最大 4 時間使い続ける。実機では配信ファイルの応答は上書きされなかったが、プランやゾーンの設定で変わりうるので、`/s/*` を Cache Rule で切り離してヘッダーを尊重させておく。手順は [デプロイガイド 2 節](deploy.md#2-edge-のデプロイ)の 2.6。

### 公開履歴の本体の保持

公開の本体(配った設定の全文)は、サイトごとに本体が残っている版を新しい順に数えて、既定で 100 版を残す。本体の無い失敗・予約の版は数えず、本体を持つ版が保持の数より少ないサイトでは何も消さない。残す数は control の `AB_PUBLISH_BODY_KEEP`(20〜10,000、未設定・空・整数でない値・範囲外は 100)で変えられる。

保持の数より古い本体は、1 日 1 回(UTC 1 時以降)の定期処理 `config-cleanup` で消す。最初の掃除などで溜まっているときも、1 サイト 1 回 500 版・1 日の全サイト合計 5,000 版まで。処理するサイトの続きがあれば、その日の次の 15 分の回に引き継ぐ。数を下げるとその後の日次の定期処理(UTC 1 時以降の最初の回。その日の処理がまだ終わっていなければ当日の回)から古い本体が消え、上げても消えた本体は戻らない。

次の版は、保持の数より古くても本体を残す。

- データベースと KV が示す配信中の版、配信ファイルが配る版以上、切り替えから 5 分以内の前の版と、5 分以内に有効になった版
- 結果の記録で配信の確認がまだ要る版
- KV の設定ファイルをまだ削除できていない版

KV を読めない・配信中の版が壊れている・配信ファイルが配る版が分からないサイトでは何も消さない。メンテナンス中も消さない。公開操作や画面の読み取りは本体の掃除を行わない。

本体を消しても、版・状態・日時・公開した人・設定の hash は公開履歴に残る。一覧の API `GET /sites/:sid/publishes` の `bodyPrunedAt` は、消した時刻(epoch ミリ秒)。`null` は本体が残っているか、もともと無い版。本体の API `GET /sites/:sid/publishes/:version`(管理者以上)は、消した版では 404 `not_found` と `hint`・`bodyPrunedAt` を返す。

D1 は本体を消して空いた領域を再利用する。データベースの大きさがすぐ下がるとは限らない。手元の計測では、512 KB の本体を持つ 520 版から 500 版を消すと `size_after` は 273,494,016 → 11,350,016 バイトになった一方、3,000 版の小さな本体の例では大きさが変わらなかった。本番の値は下の `config-cleanup` の `size_after` で確認する。値が下がらなくても、空いた領域は後の公開で再利用できる。

## 5. 開始直後のチェック

開始したら**その場で対象ページを Chrome で開く**。見るのは 4 点。

1. **対象 URL で適用されている**: パターンの変更が実際に見えること。出ないときは [10 節](#10-トラブルシュート)
2. **Console に CSP / Trusted Types の違反が無い**([サイト導入ガイド 10 節](site-install.md#10-コードの変更と-csp))
3. **`ab_exposure` が届いている**: `dataLayer` か GA4 の DebugView で確認する([サイト導入ガイド 5 節](site-install.md#5-設置後の確認))
4. **コードの変更を含むエクスペリエンスは、開始前にプレビューで `error` を確認済みである**([3 節](#3-下書きプレビュー))

### コードの変更を含むエクスペリエンスの必須手順

CUSTOM_JS だけのパターンが CSP でブロックされると、**処理群だけ Exposure が出ず**(対照群は selector で出る)、母数が片側に偏る(SRM)。これはツールのコードでは検知できないので、次の運用の手順で確かめる。

コードの変更(HTML / CSS / CUSTOM_JS)を含むエクスペリエンスは、**開始直後**に対象ページを Chrome で開き、次を確認する。

- **(a)** Console に CSP / Trusted Types の違反が無いこと
- **(b) 両群**の `ab_exposure` が出ること。割当を引き直す方法は Mode で違う: Mode A は正本 Cookie(サイト設定の `正本 Cookie 名`。新しいサイトの既定は `_wtt_vid`、それより前に作ったサイトは `_ab_vid`)を削除して再読込、Mode C は参照 Cookie の値が違う別のテスト利用者で開く(本番の認証 Cookie は消さない)、Mode B は DevTools → Application → Cookies で正本 Cookie を削除する([サイト導入ガイド 5 節](site-install.md#5-設置後の確認))。**エクスペリエンスに設定した全パターンが出るまで引き直しを繰り返す**。確認は `dataLayer` か GA4 の DebugView
- **(c)** 違反・片群の Exposure 欠落・変更の適用失敗のいずれかがあれば**すぐに一時停止**する。原因を直し、再検証してから再開する

**下書きプレビューは Exposure を送らないので、(b) の代わりにはならない**([3 節](#3-下書きプレビュー))。プレビューは「適用できるか」を見る道具、開始直後のチェックは「両群に届いているか」を見る道具である。

### 出ない理由を機械的に調べる

「なぜこの URL でこのエクスペリエンスが出ないのか」は、`evaluate`(割当の dry-run)がエクスペリエンスごとに `reason` を返す。使い方は [エージェント向けガイド レシピ 4](agent-guide.md#レシピ-4-配信条件の-what-ifなぜこの-url-で出ないのか)。

## 6. ロールと管理操作

### システム管理者

この導入(Cloudflare アカウント上の 1 デプロイ)全体を管理する人。**初回セットアップで作った最初のオーナーがシステム管理者になる**。システム管理者は、すべてのワークスペースのオーナーを兼ね(新しいワークスペースができると自動でオーナーとして入る)、次の操作を行える。

- **ワークスペースを作る・削除する**(システム管理者だけ。ワークスペースのオーナー / 管理者でも、システム管理者でなければ作れない・削除できない。左メニューの下の「設定」→「システム」の見出しの下の「ワークスペース」。一覧にサイト・メンバー・配信中の数が出る。削除はワークスペース名を打ち込んで確かめてから行い、配信中のエクスペリエンスがある・最後の 1 つのときはボタンが押せず理由が出る。API は `POST /workspaces` / `DELETE /workspaces/:wid`)
- **システム管理者を追加する・外す**: 左メニューの下の「設定」→「システム管理者」(管理画面からだけ。API キーでは行えない)。追加はワークスペースのメンバーの一覧から選ぶ(各行に参加しているワークスペースとそこでのロールが出る。まだメンバーでない人・メンバーから外した人は選べないので、先にワークスペースへ招待して受諾してもらう)。追加した人はすべてのワークスペースのオーナーになり、その人宛ての未受諾の招待は取り消される。外すと、その人が**システム管理者になる前に参加していたワークスペースでは元のロールに戻り**、それ以外のワークスペースからは外れる(確認画面に戻るワークスペースとロールが出る。最初のシステム管理者のように、なる前の参加の記録が無い人はすべてのワークスペースから外れるので、必要なら改めて招待する)。完全に外したいとき(退職など)と、信頼できなくなった人を外すときは、確認画面で「元のロールに戻さず、すべてのワークスペースから外す」にチェックを入れる(元のロールに戻すと、外すのと同時に本人が自分をシステム管理者に追加する要求を送っていた場合に、その要求が通ってシステム管理者に戻ることがあるため)。最後の 1 人は外せない(409 `last_instance_admin`)
- **配信ファイルの状態を見る・公開中の全サイトの配信ファイルを作り直す**: 左メニューの下の「設定」→「配信ファイル」(「システム」の見出しの下)。表「配置の状態」に、「更新待ちのサイト」「削除を受け付けたが、まだ消えていないサイト」「最後のエラー」「連続の失敗」「最後に成功した時刻」「記録が食い違っているサイト」「デプロイ専用の Worker の記録に無い公開中のサイト」「更新の依頼が届いていないサイト」が出る。「公開中の全サイトの配信ファイルを作り直す」は、デプロイ専用の Worker を作り直した後と、データベースを過去の時点に戻した後に使う(デプロイガイド 2.9 の補足・10.2 の手順 8)。作り直しは管理画面からだけ行える(API は `POST /static/rebuild`。API キーでは 403 `session_required`)。状態(`GET /static/status`)は、システム管理者の「すべてのワークスペース」の鍵(権限を絞らない)でも読める。配置の失敗が続いている・記録が食い違っている・状態を続けて取得できないあいだは、システム管理者の画面の上部に帯が出る

ワークスペースの側からシステム管理者に手を出すことはできない: メンバー画面ではシステム管理者の行に印が付き、ロールの変更・削除はできない(409 `instance_admin_member`)。システム管理者宛てのリセットリンクの発行と、システム管理者の API キーの失効も、システム管理者だけが行える(鍵は「メンバーの API キー」の一覧に「システム管理者」の印付きで出る)。

**システム管理者は 2 人以上にしておく**。1 人だけでその人の Google アカウントが使えなくなると、非常用の経路(デプロイガイド 8 節)でしか戻れない。

人ごとに見せるサイトを分けたいときは、ワークスペースを分けて、それぞれに必要な人だけを招待する(ロールはワークスペースごと)。

### ロール

| 操作 | オーナー | 管理者 | 編集者 | 閲覧者 |
|---|---|---|---|---|
| ワークスペースの作成・削除(システム管理者だけ。上の「システム管理者」の節) | — | — | — | — |
| ワークスペース / メンバーの管理、招待の発行・取り消し | ○ | ○ | × | × |
| サイトの作成・設定変更(mode / id_source / allowed_origins / retention / consentMode / forgetOnRevoke / 新しい訪問者の記録の上限 / 結果を記録する・参加者ごとの記録を残す日数) | ○ | ○ | × | × |
| 外部計測の名前のサイト単位(dataLayer の変数名・イベント名・キー名・`extraKey`) | ○ | ○ | × | × |
| エクスペリエンス・パターン・変更・目標の作成・編集(**コードの変更を含む**) | ○ | ○ | ○ | × |
| **本番化: 公開・開始・一時停止・終了** | ○ | ○ | × | × |
| 結果(GA4 リンク)閲覧 | ○ | ○ | ○ | ○ |
| エクスペリエンスの変更履歴の閲覧(編集者・閲覧者にはメールアドレスを出さない) | ○ | ○ | ○ | ○ |
| ワークスペースの操作の記録の閲覧(導入全体の記録はシステム管理者だけ) | ○ | ○ | × | × |
| サイトの削除 | ○ | × | × | × |

**ワークスペースを削除できるのはシステム管理者だけで、最後に残った 1 つは削除できない**(409 `last_workspace`)。配下のサイトの設置タグの配信ファイルも消す。消せないときはワークスペースを削除せずに 503 `static_remove_failed` を返すので、しばらくしてからやり直す(サイトの削除と同じ扱い。[「サイトの削除」](#サイトの削除)。削除が受け付けられた後に配信ファイルが実際に消える時期も、サイトの削除と同じ。削除を受け付けた後にまだ消えていない配信ファイルは、システム管理者の配信ファイルの画面の「削除を受け付けたが、まだ消えていないサイト」に出る)。**配下のサイトに実行中のエクスペリエンスがあるワークスペースも削除できない**(409 `workspace_has_running_experiments`。先にすべて終了する)。すべて消すと誰もログインできない状態になるため、その一手前で断る。配下のサイトの ID は、システム管理者だけが作り直せる([「サイトの削除」](#サイトの削除))。作り直したいときは先に新しいワークスペースを作り、それから古い方を削除する。ワークスペースを削除すると、そのワークスペースにしか所属していなかった人はその場でログイン状態が切れる。

境界は「作成」と「本番化」で引く。編集者はコードの変更を含むあらゆる下書きを作れるが、訪問者に届く操作(公開と状態の変更)は管理者以上に限る。編集者の資格で公開・開始を呼ぶと 403(`{"error":"forbidden","required":"admin","hint":"…"}`)になる。

### API キー

**大原則: 人とアクセス権の書き込みは管理画面から行う**。API キーの発行・一覧・失効、招待の発行・取り消し・受諾、メンバーのロールの変更・削除、リセットリンクの発行、システム管理者の追加・外す、ワークスペースの作成・削除、ログインの操作は、API キーでは行えない(403 `session_required`。鍵の種類に関わらない)。漏れた鍵で鍵を増やす・自分を招待して居座る・他人のパスワードを変える・ワークスペースを消す、といった操作を防ぐため(鍵を失効させても、増やした鍵や招待で入ったメンバーは残る)。API キーはサイト・エクスペリエンスの運用(作る・直す・公開する・読む)に使う。読み取り(メンバー・招待の一覧など)は鍵でもできる。

API キーは、非常用のパスワードログイン([デプロイガイド 8 節](deploy.md#8-非常時の入り方))でログインしたセッションからは発行できない(403 `password_session`)。非常口を閉じても、開いているあいだに発行した鍵は残るため。Google でログインし直してから発行する。自分の鍵の一覧と失効は、パスワードでログインしたセッションでもできる。

管理画面の左メニューの下の「設定」→「API キー」(「個人」の見出しの下)の「新しい API キーを発行」で発行する。項目は 4 つで、すべて選ぶまで発行できない: **名前**(どこで何に使うキーか)/ **範囲**(**ワークスペース** = 選んだ 1 つだけで使える。そのワークスペースのメンバーなら発行できる。**すべてのワークスペース**(API の値は `full`)= システム管理者だけが発行・使用できる)/ **権限**(閲覧者 / 編集者 / 管理者 / 本人と同じ。範囲での自分のロール以下だけが選べる。API の `roleCap`)/ **有効期限**(期限なし / 1 日 / 7 日 / 30 日 / 90 日。期限は発行した時刻から数え、選ぶと期限の日時が横に出る。API の `expiresInDays` は 1〜365 の整数で、省略すると期限なし。更新や確認のためだけに使う鍵は 1 日にする。期限を過ぎた鍵は 401)。一覧の「期限」の列に期限の日時(過ぎた鍵は「期限切れ」)が出る。範囲外のワークスペースは鍵からは見えない(404)。キーの実際の権限は **そのワークスペースでの持ち主のロールと、選んだ権限の低い方** になる(権限は付与ではなく、ロールより上には行かない。ロールが下がればキーの権限も下がる)。**キーは発行の直後に 1 度だけ表示され**、「保管したので閉じる」を押すまで次の発行はできない(控えずに別の画面へ移ろうとすると確認が出る)。以後はハッシュしか保持しないので、控え忘れたら失効させて発行し直す。鍵は、持ち主が範囲を使えなくなると(すべてのワークスペースの鍵 = システム管理者から外れた、ワークスペースの鍵 = そのワークスペースから外れた・ワークスペースが削除された)その時点から 401 になる。メンバーから外すと、その人のそのワークスペースの鍵は失効する(メンバーに戻しても使えない)。システム管理者から外したときは、「すべてのワークスペース」の鍵と、外れたワークスペース(元のロールに戻らないワークスペース)の鍵が失効する。エージェントに下書きだけ作らせるなら、権限を「編集者」にする。誰の操作かをメンバーの一覧で見分けたいときは専用のユーザーを作り(専用の Google アカウントのメールアドレスで招待する)、そのユーザーで発行する。**管理者以上は、左メニューの下の「設定」→「メンバーの API キー」(「ワークスペース」の見出しの下。ワークスペースかサイトの画面から開いたときに出る)で、そのワークスペースで使えるキー(そのワークスペースの鍵と、システム管理者の「すべてのワークスペース」の鍵)を持ち主・範囲・権限・最終使用日付きで一覧でき、失効させられる**(自分のキーの画面の下にも、管理者以上であるワークスペースへのリンクが出る。API は `GET /workspaces/:wid/api-keys` / `DELETE /workspaces/:wid/api-keys/:kid`)。「すべてのワークスペース」の鍵を失効させると、どのワークスペースでも使えなくなる。オーナーのキーを失効できるのはオーナーだけ。失効させた鍵と期限を過ぎた鍵は、使えなくなった時刻(失効か期限切れの早い方)から 30 日間一覧に残り(失効させた鍵は「失効済み」に名前・接頭辞・発行日・失効日、期限を過ぎた鍵は期限の列に「期限切れ」。接頭辞はどの鍵も同じ `wtt_` で、鍵そのものは分からない)、その後は自分の一覧を開いたときに消える。失効した鍵はその時点から認証に通らない(失効の記録は鍵の行とは別に持つので、失効と同時に使われていた要求があっても失効は消えない)。

### ログイン

管理画面へのログインは **Google アカウント**で、入れるのは招待されたメールアドレスだけ。受け取るのはメールアドレスとプロフィールだけで、**Google のトークン(アクセストークン・ID トークン)は保存しない**。ログイン後に Google の API を呼ばないため。メール + パスワードの経路は普段閉じており、開いているあいだは、管理画面にログインしているあいだどのページにも注意の帯が出る(ログイン前の画面には出ない)。閉じた後、通常 15 分以内に、パスワードの記録と、パスワードの記録を持つ人のログイン状態(Google でログインしたものを含む)が消えるので、非常時にパスワードを使った人は 1 回 Google でログインし直す([デプロイガイド 8 節](deploy.md#8-非常時の入り方))。

### メンテナンス中(書き込みの凍結)

更新などの間、管理画面の上部に「メンテナンス中のため、変更は保存できません」の帯が出る。この間は保存・公開・エクスペリエンスの開始と一時停止・招待の受諾などができない(押すと理由が表示される。入力は消えない)。閲覧とログインはでき、訪問者への配信も続く。帯が消えてから(開いたままの画面でも 1 分ほどで消える)、もう一度保存する。エクスペリエンスの編集画面で「一部は保存されています」と出た場合も、画面を再読み込みせずに、帯が消えてからもう一度保存すると残りも保存される。帯が「再開の見込みを過ぎています」のまま続くときは、更新の作業者に確認する(凍結は作業者が外すまで続く)。

### 管理画面の版の帯

管理画面と control はそれぞれ自分の版を名乗り、食い違うと管理画面の上部に帯が出る(開いたままの画面にも 1 分ほどで出る)。v0.11 より前に開いた画面には帯が出ない。保存すると「管理画面が古い版です」(426)で断られるので、再読み込みする。

| 帯の文言 | 意味 | すること |
|---|---|---|
| 管理画面の新しい版があります。この画面のままでは保存できません。ページを再読み込みしてください(未保存の入力は消えます)(目立つ帯) | 更新の前に開いた画面で、control がこの画面からの保存を受け付けない。保存すると「管理画面が古い版です」(426)で断られる | 未保存の入力を控えてから、ページを再読み込みする |
| 管理画面の新しい版があります。ページを再読み込みすると反映されます(控えめな帯) | 新しい版の管理画面がある。この画面のままでも保存はできる | 区切りのよいところで再読み込みする |
| サーバー側(control)が管理画面より古い版です。更新の途中か、control の更新が漏れています。作業者に確認してください | 管理画面だけが先に更新されている | 更新の作業者に確認する。更新の途中なら終わるまで待つ |

### ログインできなくなったとき

- **メンバーが入れない**: 通常は Google アカウント側の問題なので、Google の復旧手順で直す(パスワード再設定、2 段階認証の端末変更など)。招待されたメールアドレスと違う Google アカウントでは入れない
- **「どのワークスペースにも所属しておらず、有効な招待もありません」と出る**: Google でログインしたときは、control のアドレスで開く「ログインできませんでした」の画面(理由のコード `not_invited`)に、非常用のパスワードでログインしたときは、管理画面のログイン画面に出る。この文言は、(a) そのメールアドレスが招待されていない(招待されたのと違う Google アカウントで入ろうとした場合を含む)、(b) メンバーから外された・招待を取り消された、のどちらかである。心当たりが無ければ、ワークスペースのオーナー・管理者に、そのメールアドレス宛ての招待を発行してもらう。非常用のパスワードログインが開いているときも、同じ理由なら同じ文言で断られる(パスワードの誤りではない)
- **「この Google アカウントを、同じメールアドレスの既存のアカウントに結びつけられませんでした」と出る**: control の「ログインできませんでした」の画面(理由のコード `account_not_linked`)に出る。まず、その Google アカウントのメールアドレスが Google 側で確認済みかを確かめる(未確認ならログインに使えない)。確認済みなら、その人は非常用のパスワードログイン([デプロイガイド 8 節](deploy.md#8-非常時の入り方))で作られ、まだ Google でログインしたことのない人である。そのような人は、Google アカウントに自動では結びつかない。ワークスペースの管理者が同じメールアドレスで招待し直すと、招待を出したときにその人の古い記録が消え、本人が Google で招待を受けると入れる。古い記録が消えるのは、招待を出す時点で次の 4 つをすべて満たすときだけである。1 つでも欠けると、招待は出るが古い記録が残り、Google でのログインは同じ文言で断られたままになる。そのときは欠けているものを満たしてから、招待を取り消して出し直す
  1. **システム管理者でない**: システム管理者なら、2 より先に、左メニューの下の「設定」→「システム管理者」のその人の行の「システム管理者から外す」で外す(システム管理者のままでは、ワークスペースのメンバー画面から外せない)。確認画面に「元のロールに戻さず、すべてのワークスペースから外す」のチェックが出ていれば入れる(入れないと元のロールに戻り、またどこかのワークスペースのメンバーになる)。その人が唯一のシステム管理者なら外せない。そのときは、デプロイガイド 6.3 の「ログインのライブラリを上げるリリースの更新」にある、その人を確認済みにする手順(本人の行の `id` を読むだけの SQL で確かめてから、その `id` の行だけを書き換える)で直す。この手順は更新の後に流しても効果は同じで、条件も同じ(先に非常口を閉じ、15 分ごとの定期処理でパスワードの記録が消えるのを待つ)。確認済みになった人は、招待し直さなくても Google でログインできる
  2. **どのワークスペースのメンバーでもない**: その人がまだメンバーのワークスペースがあれば、それぞれのメンバー画面のその人の行の「外す」で外す
  3. **Google のアカウントが結びついていない**: この文言が出る人は、Google で一度もログインできていないので当たる
  4. **ログインしたままの状態が残っていない**: パスワードでログインした状態は、非常口を閉じた後の 15 分ごとの定期処理で消える(デプロイガイド 8 節)。そのため、非常口を閉じてから、通常 15 分たった後に招待し直す

  古い記録が消えると、その人の API キーとパスワード再設定リンクも消える。その人が出していた未使用の招待は、招待し直した管理者が出した招待として残る。受けられるのはその管理者がメンバーのワークスペースのものだけなので、ほかのワークスペースの招待は取り消して出し直す
- **「ログインできませんでした」の画面から先に進めない**: この画面は Google ログインの失敗をすべて受ける。管理画面へのリンクは置いていない(ログインしていない人に管理画面のアドレスを知らせないため)。管理画面のログイン画面(ブックマーク)か、招待リンクを開き直してログインし直す。理由のコードが `oauth_failed` で何度も出るときは、ログインを始めてから 10 分以上たっていないか、Cookie を拒む設定になっていないかを確かめる。`rate_limited` のときは、同じ送信元(同じ拠点など)から短い時間にログインが集中している。少し待ってからやり直す(枠は 7 節の値)。`google_not_configured` のときは、control に Google の OAuth クライアントが設定されていない([デプロイガイドの Google の OAuth クライアントの手順](deploy.md#05-人に用意してもらうもの一度に集める))
- **オーナーが入れない**(OAuth クライアントを消した・壊した、Google 側の障害): [デプロイガイド 8 節「非常時の入り方」](deploy.md#8-非常時の入り方)。Cloudflare で control の secret を設定できる人だけが、非常用トークンでオーナーのパスワード再設定リンクを得られる。用が済んだらトークンを消す
- **非常用の経路が開いているあいだのパスワードリセット**: メール送信基盤は持たない。対象ユーザーが所属するワークスペースの**メンバー画面で、その人の行の「リセットリンク」**を押し、発行されたリンクを本人に手渡しする(発行先のワークスペースで管理者以上の人が、発行先だけに所属する人か自分自身に発行できる。対象が他のワークスペースにも所属するときは、そのすべてでオーナーの人かシステム管理者だけが発行できる。オーナー宛のリンクを発行できるのはオーナーのみ。再設定すると、その人のそれまでのログイン状態はすべて切れる。招待を受けたりロールが変わったりすると、その前に発行されたリンクは使えなくなる)。リンクは管理画面の `/reset?token=…` 形式。非常用の経路が閉じているときは発行できない(409 `password_login_disabled`)。リンクを開いて失敗するときは、まず再設定画面の案内どおり URL が途中で切れていないか(末尾までコピーしているか)を確認する。それでも開けなければ期限切れか使用済みなので、リンクを発行し直す

### 招待

招待リンクは**発行から 7 日で失効する**。メールは送らないので、発行者が手渡しする。受ける側は、**招待されたメールアドレスと同じ Google アカウントでログインして**受諾する(別のメールアドレスの Google アカウントでは受けられない)。

- **いつ切れるかを見る**: 招待一覧の「期限」列に、切れる日時(見ている人のタイムゾーン)と残り(「あと 3 日」「あと 5 時間」など)が出る。期限は**発行または延長した時刻から 7 日ちょうど**で切れる(その日の終わりではない)
- **期限を延ばす**: 招待一覧の「期限を延ばす」を押すと、その時点から 7 日後まで延びる。**リンクは変わらない**ので、相手に渡し直す必要はない。既に切れている行のボタンは「発行し直す」になり、こちらは**新しいリンク**になる(古いリンクは使えない。渡し直すこと)。同じメールアドレス・同じロールでもう一度「招待リンクを発行」しても同じ結果になる
- **ロールを変えたい**: **先にその招待を取り消してから、新しいロールで発行し直す**。既に招待済みのメールアドレスを違うロールで招待しようとすると、現在のロールを示して断られる(API では 409 `already_invited`)。黙ってロールが変わらないまま期限だけ延びることはない
- **招待された人がログインしたのにワークスペースが何も出ない**: 招待リンクを開かずに、ログイン画面から直接ログインしている。招待されたメールアドレスならログイン自体は通るが、**ワークスペースに入るのは招待リンクを開いて「この招待を受ける」を押したとき**である。この状態ではホームに「まだどのワークスペースにも参加していません」という案内が出るので、招待リンクを開き直すよう伝える。ログインしたまま招待リンクを開き直せば受諾できる。招待を渡すときは「このリンクから入ってください」と添える
- **発行した招待を取り消す**: **オーナー・管理者**が、ワークスペースのメンバー画面の招待一覧にある「取り消す」で行う(API では `DELETE /workspaces/:wid/invitations/:id`)。取り消した招待のリンクはその場で使えなくなり、一覧からも消える。一覧に並ぶのは**まだ受けられていない招待だけ**で、受諾済み・取り消し済みの招待は出ない。メールアドレスを間違えて発行したときは、取り消してから正しいアドレスで発行し直す
- **メンバーから外す / 招待を取り消すと、その人はログインできなくなる**: 他のワークスペースに所属しておらず、別の有効な招待も無ければ、その時点で**ログイン中の状態もその場で切れ**(次の操作から画面がログインに戻る)、以後は新しくログインすることもできない。API キーも同じで、ワークスペースに触れない。他のワークスペースに所属している人・別の有効な招待がある人のログイン状態は切れない。外した人を戻すときは招待し直す

### サイトの削除

**オーナーのみ**。サイト設定の変更が管理者以上なのに対し、削除は取り返しがつかないので、オーナーだけに限っている。**配信中のエクスペリエンス(状態または公開済みのいずれかが `running`)があるサイトは削除できない**(409 `site_has_running_experiments`)。先に終了してから削除する。削除しても Visitor Profile は即時には消えない([8 節](#8-既知の制約))。

設置タグの配信ファイルも消す。消せないときはサイトを削除せずに 503 `static_remove_failed` を返すので、しばらくしてからやり直す。**削除の成功(204)は「削除の依頼を受け付けてサイトの記録を消した」ことで、配信ファイルそのものは配信を管理する Worker がその依頼を Cloudflare に反映した時点で消える**(通常は数秒。Cloudflare の API が失敗したときは 30 秒・2 分・10 分・以後 1 時間ごとに再試行し、成功するまで最後に配信していた内容が残る)。削除を受け付けた後にまだ消えていない配信ファイルは、システム管理者の配信ファイルの画面(左メニューの下の「設定」→「配信ファイル」)の「削除を受け付けたが、まだ消えていないサイト」に出る。削除したサイトの設置タグをページに残している場合、配信ファイルが消えると 404 になり、runtime は起動しない(元の表示のまま)。削除の途中で「配信ファイルを作り直す」が押されると、409 `static_remove_conflict` で削除を取りやめる。削除が途中で止まったサイトには、画面に「このサイトの削除が途中で止まっています」が出る。もう一度削除するか、「配信ファイルを作り直す」で配信を戻せる。

**削除したサイトの ID は、そのサイトがあったワークスペースでだけ作り直せる。** 別のワークスペースで同じ ID のサイトは作れない(409 `site_id_taken`)。削除したサイトの設置タグがページに残っていても、ほかのワークスペースの人がその ID を取って、そのタグを使うことはできない。誤って削除したサイトを同じワークスペースで作り直し、既存のタグを引き継ぐ使い方は、今までどおりできる。作り直せるのは、そのサイトがあったワークスペースの管理者以上とシステム管理者。ワークスペースごと削除したサイトの ID は、システム管理者だけが、別のワークスペースにも作り直せる。ID の記録は、期限がなく消えない。

作り直したサイトは、削除したサイトの訪問者の履歴(オーディエンスの条件などに使う記録)を、保持期間が過ぎて消えるまで引き継ぐ。履歴を引き継げるのは、そのサイトがあったワークスペースでの作り直しと、システム管理者の取り直しに限る。システム管理者が別のワークスペースに取り直したときは、取り直した先のワークスペースのメンバーが、その履歴をオーディエンスの条件などに使える。

**この記録は、v0.11 に更新した後に削除したサイトの ID だけに付く。** それより前に削除したサイトの ID は守られないので、そのタグがページに残っているなら、ページから外す。

### 操作の記録と変更履歴

control は、人とアクセス権の操作と、サイト・エクスペリエンス・目標・オーディエンス・公開の変更を、1 回の操作ごとに 1 行の要約で記録する。1 行には、いつ・誰が・どのログイン方法か API キーで・どの対象に・何をしたか(前後の値・件数・値が変わった項目の名前など)が入る。記録はこの機能を入れた版に更新した後の操作からで、それより前の操作は無い。

| 見る場所 | 見られる人 | 中身 | API |
|---|---|---|---|
| エクスペリエンスの画面の「変更履歴」タブ | そのワークスペースのメンバー全員(閲覧者を含む) | そのエクスペリエンスの記録 | `GET /sites/:sid/experiments/:eid/history` |
| 左メニューの下の「設定」→「操作の記録」(「ワークスペース」の見出しの下) | そのワークスペースの管理者以上 | そのワークスペースのすべての記録(人とアクセス権・サイト・エクスペリエンスなど) | `GET /workspaces/:wid/audit-events` |
| 左メニューの下の「設定」→「操作の記録」(「システム」の見出しの下) | システム管理者 | 導入全体の記録(すべてのワークスペースと、システム管理者・使用状況の設定・非常口・パスワードでのログインなど、どのワークスペースにも属さない操作) | `GET /audit-events` |

- **メールアドレスは管理者以上にだけ出す**。編集者・閲覧者(と、権限が編集者・閲覧者の API キー)には、操作した人は名前だけを出す(名前が空か、名前がメールアドレスの形ならメールアドレスの @ より前)。対象の人・招待の宛先は、名前の有無を問わずメールアドレスの @ より前だけを出す。API キーの名前も、メールアドレスの形なら @ より前だけを出す
- API はどれも API キーで読める。使える鍵と読み方は[エージェント向けガイド レシピ 8](agent-guide.md#レシピ-8-操作の記録と変更履歴を読む)

#### 記録する操作

- **人とアクセス権・導入の設定**: 招待の発行・取り消し・受諾、ロールの変更、メンバーから外す、パスワードの再設定リンクの発行(メンバー画面から・非常用トークンで)、システム管理者に追加する・外す、API キーの発行と失効(自分の鍵・メンバーの鍵)、ワークスペースの作成・削除、初期設定の完了、使用状況の設定の変更、公開中の全サイトの配信ファイルの作り直し、パスワードでのログイン、非常口を閉じた後の掃除(パスワードの記録とログイン状態を消したときだけ)
- **サイト・エクスペリエンスなど**: サイトの作成・サイト設定の保存・削除、エクスペリエンスの作成・基本設定の保存・メモ・パターンの構成・パターンのメモ・パターンの変更・状態の変更(開始・一時停止・再開・終了)・採用・複製・削除・評価計画、目標とオーディエンスの作成・変更・削除、画像のアップロード・名前の変更・削除待ちにする操作、公開、サイトの配信ファイルの作り直し
- **記録しないもの**: Google でのログインとログアウト、再設定リンクを開いてパスワードを決める操作(リンクの発行と、その後のパスワードでのログインは記録する)、配信条件の確認(`evaluate`)、定期処理が自動で行う書き込み(結果の集計・配信ファイルの整合・削除待ちの画像の削除と一覧への戻し・縮小版の作成など。非常口を閉じた後の掃除だけは記録する)。中身では、変更(HTML・CSS・JS)と配信条件の前後の違い・メモの本文・IP アドレスを持たない。公開した版の中身は公開履歴で見る

#### 読み方

- **1 回の保存が複数の行になる**: 管理画面のエクスペリエンスの保存は、変えた部分(基本設定・メモ・パターン・パターンのメモ・パターンごとの変更)ごとに別の要求で送るので、記録も部分ごとに 1 行ずつ並ぶ
- **内容の欄**: 前後の値(ロール・状態・名前・配信率など)・件数・値が変わった項目の名前を出す。サイト設定・エクスペリエンスの基本設定・評価計画・目標・オーディエンス・使用状況の設定の保存は、保存の時点の値と比べて値が変わった項目だけを記録する(同じ値を送り直した項目は出ない)。変わった項目が 1 つも無い保存は「項目の変更なしの保存」と出る。パターンの構成とパターンの変更の行は前後(パターンの名前と重み・変更の件数)をそのまま持つので、前後が同じなら「(変わらず)」と出る。サイト設定の長い値の欄(タグを置くドメインなど)は名前だけを出す
- **「…を受け付け」と「…を試みたが失敗」**: API キーの発行とパスワードの再設定リンクの発行(メンバー画面から・非常用トークンで)は、操作の前に記録を書き(書けなければ操作をしない)、画面には「…の発行を受け付け」と出る。その後で操作が失敗したら失敗の行(「…を試みたが失敗」)を足す。API キーの発行が成功すると、鍵の ID を持つ成功の行(「API キーを発行」)がもう 1 行付く。再設定リンクの発行には成功の行が付かないので、失敗の行が続かなければ発行は通ったと読む(失敗の行は操作の後に書くので、欠けることがある。下の「記録が欠けるとき」)。公開中の全サイトの配信ファイルの作り直しも始める前に書き、「すべてのサイトの配信ファイルの作り直しを受け付け」と出る。作り直しには成功の行も失敗の行も付かない(サイトごとの結果は、作り直しの応答と配信ファイルの画面で見る)
- **戻しの行**: 「公開を戻した」(配る設定の書き込みに失敗して公開を取り消した)・「保存を戻した」(サイト設定の保存の途中で失敗して戻した)・「作成の取り消し」(サイトの作成の途中で失敗して取り消した)。記録は消せないので、取り消しも行を足して表す
- **ログイン方法**: Google / パスワード / API キー(鍵の名前を添える)/ 非常口(非常用トークン)/ 初期設定 / 定期処理 / 不明(ログインの方法の印を持たないログイン状態)。パスワードと非常口には黄の印が付く。エージェントの操作を見分けやすいように、鍵の名前は用途が分かるものにする
- **招待の受諾**: 入った人は「操作した人」の欄に出る(受諾は招待のメールアドレスと同じ人しかできない)。招待のリンクからパスワードでアカウントを作った受諾は、ログイン方法がパスワードになる
- **時刻**は見ている人のタイムゾーンで出す。名前・メールアドレスは記録した時点の控え。操作した人が消えた後は、メールアドレスは出さず控えの名前だけを出す(対象の名前・宛先は、対象が消えても残る)
- **変更履歴のタブ**には、今のエクスペリエンスの記録だけが出る。同じ ID で作り直したエクスペリエンス・サイトでは、前のものの記録は出ない(消したエクスペリエンスの記録は、ワークスペースの操作の記録で読む)。記録を始める前に作ったエクスペリエンスでは、表の下に「作成: 名前(日付)・最後に変えた人: 名前」と出す
- **絞り込み**(設定の「操作の記録」): 期間(7・30・90・365 日。または開始と終了の日時)・種類(すべて / 人とアクセス権 / サイト・エクスペリエンス)・「パスワードのログイン・非常口だけ」・操作した人(読み込んだ記録の中で絞る)。一覧は 100 件ずつで、「さらに 100 件を読み込む」で続きを読む。非常口を閉じた後は、導入全体の記録(「システム」の見出しの下。システム管理者)で確かめる。手順は[デプロイガイド 8 節](deploy.md#8-非常時の入り方)の「閉じた後の注意」

#### 保持と守り

- 記録は **365 日**残す。control の定期処理が 1 日 1 回(UTC 19 時以降)、366 日より前の記録を消す(1 日に最大 5,000 行。それより多いときは翌日以降に続ける)
- 記録を書き換える・消す画面と API は無い。データベースのトリガーが、記録の書き換えと、365 日より新しい記録の削除を断る。ただし、Cloudflare のアカウントで D1 を直接操作できる人(`wrangler d1 execute`)はトリガーごと変えられる(ほかのデータと同じ)ので、その権限は運用に要る人に絞る
- D1 を過去の時点に戻すと、記録も戻した時点のものに戻る。戻す前に、その後の記録を控える([デプロイガイド 10.2](deploy.md#102-d1-を過去の時点に戻すtime-travel) の手順 4)
- 書き込みの凍結中は、記録を伴う操作そのものが断られる。凍結の対象外のパスワードでのログインと、非常用トークンでの再設定リンクの発行は、凍結中も記録する

#### 記録が欠けるとき

- 招待の発行・受諾・パスワードでのログインと、API キーの発行の成功の行(鍵の ID を持つ行)、API キーの発行とパスワードの再設定リンクの発行の失敗の行(「…を試みたが失敗」)は、操作の後に別に書く。D1 が一時的に失敗すると、操作は成功のまま記録だけが欠け、control のログ([10 節「Cron の回の結果を後から読む」](#cron-の回の結果を後から読む)の Workers Logs)に `audit: failed to record` の行が出る(メールアドレスは出さない)。ほかの操作は、記録が書けなければ操作ごと失敗する(500)ので、記録だけが欠けることは無い
- control を前の版に戻しているあいだの操作は記録されない

#### 控え(メールアドレス・名前)を消すよう求められたとき

画面と API には、控えを消す道を作っていない。権限を持った人のアカウントが乗っ取られたときに、その痕跡を消させないため。本人などから求められたときは、Cloudflare のアカウントで D1 を操作できるシステム管理者が、次の手順で wrangler から消す。**記録の行と利用者 ID は残り**、その人の名前とメールアドレスの控えだけが空になる(画面の操作した人の欄には「(名前なし)」と出る。対象の欄には、人なら利用者 ID、招待なら招待の ID が出る)。コマンドはリポジトリ直下で流す。

1. その人の利用者 ID を探す。メールアドレスを変えたことがあれば、使ったメールアドレスごとに流す(`<メールアドレス>` は小文字で書く)。出た ID をすべて控える:

   ```bash
   pnpm -C apps/control exec wrangler d1 execute wtt-control --remote --command "select actor_user_id as user_id from audit_events where lower(actor_email) = '<メールアドレス>' union select target_id from audit_events where target_type = 'user' and lower(target_label) = '<メールアドレス>' union select id from \"user\" where lower(email) = '<メールアドレス>'"
   ```

2. 書き換えを断るトリガーを一時的に外し、控えの列(操作した人の `actor_email`・`actor_name`、対象の `target_label`、メンバーの API キーの失効の行の持ち主のメールアドレス `detail_json` の `owner`、鍵の名前にそのメールアドレスを入れていたときの鍵の名前の控え `api_key_name` と、対象が鍵の行の `target_label`)を空にして、トリガーを戻す。`('<利用者 ID>')` は 2 か所とも、括弧の中を手順 1 の ID にする(`('id1')`。複数なら `('id1', 'id2')`。1 つも出なければ `('')` にする。どの行にも当たらない)。`<メールアドレス>` は小文字で書く。メールアドレスが複数なら、手順 2・3 をアドレスごとに流す(利用者 ID は毎回同じでよい)。ファイルにはメールアドレスが入るので、所有者だけが開ける `deploy-backups/` に作り、流した後に消す。365 日の削除を断るトリガーは外さない:

   ```bash
   mkdir -p "$PWD/deploy-backups" && chmod 700 "$PWD/deploy-backups" && cat > "$PWD/deploy-backups/clear-snapshot.sql" <<'SQL'
   DROP TRIGGER audit_events_no_update;
   UPDATE audit_events SET actor_email = NULL, actor_name = NULL WHERE actor_user_id IN ('<利用者 ID>');
   UPDATE audit_events SET target_label = NULL WHERE (target_type = 'user' AND target_id IN ('<利用者 ID>')) OR (target_type = 'invitation' AND lower(target_label) = '<メールアドレス>');
   UPDATE audit_events SET detail_json = json_set(detail_json, '$.owner', NULL) WHERE action = 'api_key.revoke_member' AND lower(json_extract(detail_json, '$.owner')) = '<メールアドレス>';
   UPDATE audit_events SET api_key_name = NULL WHERE lower(api_key_name) = '<メールアドレス>';
   UPDATE audit_events SET target_label = NULL WHERE target_type = 'api_key' AND lower(target_label) = '<メールアドレス>';
   CREATE TRIGGER audit_events_no_update BEFORE UPDATE ON audit_events
   BEGIN SELECT RAISE(ABORT, 'audit_events is append-only'); END;
   SQL
   ```

   ファイルの `<利用者 ID>`・`<メールアドレス>` を書き換えてから流し、ファイルを消す:

   ```bash
   pnpm -C apps/control exec wrangler d1 execute wtt-control --remote --file "$PWD/deploy-backups/clear-snapshot.sql" -y && rm "$PWD/deploy-backups/clear-snapshot.sql"
   ```

3. トリガーが戻り、控えが残っていないことを確かめる:

   ```bash
   pnpm -C apps/control exec wrangler d1 execute wtt-control --remote --command "select (select count(*) from sqlite_master where type = 'trigger' and name = 'audit_events_no_update') as no_update_trigger, (select count(*) from audit_events where lower(actor_email) = '<メールアドレス>' or lower(target_label) = '<メールアドレス>' or lower(api_key_name) = '<メールアドレス>' or lower(json_extract(detail_json, '\$.owner')) = '<メールアドレス>') as remaining"   # 期待: no_update_trigger 1・remaining 0
   ```

   `no_update_trigger` が 0(途中で止まった)なら、手順 2 のファイルの最後の 2 行(`CREATE TRIGGER` から)だけを `--command` で流してトリガーを戻す。

- 消した値も、D1 の Time Travel の保持期間(Workers Free は 7 日、Workers Paid は 30 日)と、運用者が取った控え(export)には残る
- この手順が変えるのは記録の表だけ。その人がまだ利用者として残っていれば、メンバーの一覧などのメールアドレスはそのまま

#### 制御用のデータベースの大きさ

記録は、サイト・エクスペリエンス・メンバーなどと同じ制御用のデータベース(D1 の `wtt-control`。Free は 1 データベースあたり 500 MB、Paid は 10 GB)に入る。1 回の記録は 1 行(索引を含めて約 0.6 KB)。365 日分の目安は、記録が 1 日 85 行ほど(保存が 50 回ほど。1 回の保存が複数の行になる)の導入で約 3 万行(約 19 MB)、1 日 800 行ほどの大きな導入で約 29 万行(約 175 MB。500 MB の約 35%)。

- 大きさは control が 1 日 1 回(上の保持の定期処理の後)測り、左メニューの下の「設定」→「Cloudflare 使用状況」の「制御用のデータベース」に出す([11 節](#11-使用状況cloudflare-の上限))。使用状況の取得を設定していない・Cloudflare からの取得に失敗した(`GET /usage` が 503)ときも、大きさは出る。まだ測っていなければ「まだ測っていません(1 日 1 回測ります)」と出る
- 上限は Free の 1 データベースの上限 500 MB と比べ(Paid の上限は 10 GB だが、目安として同じ 500 MB と比べる)、80% 以上で注意、95% 以上で危険の帯を出す。API は `GET /usage` と `GET /usage/settings` の `controlCapacity`(`level` が `ok` / `warning` / `critical`。まだ測っていなければ `controlCapacity` 全体が `null`)。Free で 500 MB に達すると、管理画面と API からの保存・変更が失敗する。空きを作るには、要らなくなったサイト・エクスペリエンスを削除する(記録は 365 日で消える)

## 7. レート制限の実効

2 つのレート制限があり、効き方がまったく違う。

### edge(訪問者のブラウザが直接叩く経路)

`/v1/sites/*`(decision / event)に、IP あたりの Rate Limiting binding を掛けている。上限は**導入時に決めた値**で、ゾーンの WAF がある構成では大きめの値(既定 1000 回 / 10 秒)、WAF が無い構成では設定値 `edge_waf_requests_per_10s`(既定 200 回 / 10 秒)にする([デプロイガイド 2.3](deploy.md#23-route-を書く))。binding は 1 つの IP からの合計で数え、WAF の NAT 支援や送信元の除外は引き継がない。Mode B(サーバー発行 Cookie)では、`/__ab/decision` に同じ binding を掛けている。同意の撤回(`kind: "consent"`)はこの制限より前に処理するので、binding の 429 で撤回が止まることは無い(撤回が届かないと Cookie が消えず、訪問者は撤回できたと思い込むため)。`/__ab/event` は binding の対象外で、ゾーンの WAF で受ける。ただし WAF の遮断は Worker が動く前に起きるので、WAF の上限に達した IP からの撤回は、`/__ab/decision` でも止まりうる。

そのうえ Workers の binding 自体が permissive で結果整合なので、本番の負荷では制限が掛からなかったという実測がある。**実効的な守りはゾーンの WAF Rate Limiting Rule**([デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨))のほうで、`/v1/sites/*` と `/__ab/*` の両方をこれで受ける。WAF が遮断した要求は、ダッシュボードの Security Events で見られる(手順は[デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨) の「遮断を見る」)。

### control(無認証の入口 11 経路)

`auth/google/start`(Google へ送り出す)/ `auth/callback/google`(Google からの戻り)/ `auth/handoff/exchange`(ログイン直後に管理画面がセッションを受け取る使い捨てコードの交換)/ `break-glass/reset-link`(非常用トークンの照合)/ `setup` / 招待受諾 / `auth/sign-out`(ログアウト)と、非常時だけ開くパスワードの 4 経路(`auth/sign-in/email` / `auth/sign-up/email` / `auth/request-password-reset` / `auth/reset-password`)に、**経路ごとに 30 回 / 10 秒**を掛けている。Google へ送り出す経路と Google からの戻りは、HEAD の要求も GET と同じ枠で数える。ログアウトは、control の公開のアドレスに直接届いた要求だけを数え、管理画面のログアウトのボタンから届く要求は数えない(枠に当たると、ログイン状態が残ったまま管理画面の Cookie だけが消えるため)。1 つの送信元 IP から、経路ごとに 10 秒に 30 回まで通す。同じ拠点(NAT)から研修などで 30 人規模が一斉にログインしても止めないための値。ログインのライブラリに内蔵されたレート制限は使っておらず、control の制限はこの binding だけ。

`GET /login-options` は無認証で、非常口が開いているかどうかが分かる。守りは sign-in のレート制限と、開いている間の管理画面の帯(と、用が済んだら secret を消す運用)。

**管理画面からの要求も利用者ごとに数える**: レート制限のキーになるのは、操作した人の IP。管理画面からの操作は「ブラウザ → admin の BFF → control」と流れる。BFF は control を service binding(同じ Cloudflare アカウントの Worker 同士の内部の接続。[デプロイガイド 4 節](deploy.md#4-admin-のデプロイ))で呼び、BFF が受けた要求の接続元 IP(Cloudflare が実際の接続元で上書きする `CF-Connecting-IP`)を control に渡す。control はその IP で数えるので、誰かがログインの枠を使い切っても、ほかの人のログインは止まらない。control の公開の入口に届いた要求からは、この受け渡しのヘッダーを消してから処理するので、外から別の IP を名乗ることはできない。

binding が無い構成(手元の開発の `pnpm admin:dev` など、admin が公開 URL で control を呼ぶ場合)だけは、control から見た接続元が admin からの接続元になるので、経路ごとに全員で 1 枠を共有する。

control の無認証の入口を直接呼ぶ要求(curl、ブラウザが直接開く Google ログインの 2 経路)も、クライアントの実 IP で数える(API キーを使う呼び出しは、この制限の対象外)。管理画面の BFF の通信は control のゾーンを経由しないので、control に掛けたゾーンの WAF と Cloudflare Access には数えられない([デプロイガイド 7 節](deploy.md#7-無認証入口の防御))。

**運用者にとっての意味**

- 管理者が数人〜十数人なら、手作業で 30 回 / 10 秒の上限に当たることはまず無い。当たるのは自動化された連続ログイン。CI や運用スクリプトから繰り返しログインする場合は枠を数える
- ログインの総当たり(ブルートフォース)への対策を強めたいなら、ゾーン側の WAF か Cloudflare Access を前段に置く([デプロイガイド 7 節](deploy.md#7-無認証入口の防御))。control に掛けたものは control への直接の要求だけが対象なので、管理画面からの要求も絞るなら管理画面にも Access を掛ける([デプロイガイド 4.5](deploy.md#45-任意-cloudflare-access-で管理画面の到達を絞る))
- limiter 自体が壊れたときは、edge / control とも **fail-open**(通してログに残す)

### 429 が訪問者に与える影響

**decision が 429 を受けた runtime は再試行せず、元の表示のままになる**。サイトは壊れないが、エクスペリエンスは適用されず Exposure も出ない。目標は、`dataLayer` への `ab_conversion` の push が行われて GA4 に届き、欠けるのは `needsProfile` のサイトの `/event` 転送(Profile の `converted` 履歴)だけ。`needsProfile: false` のサイトは decision を呼ばないので影響しない。ただし結果を記録するサイトは、テストの参加と目標の達成を `/v1/*`(`/event`)に送る。この送信が 429 を受けると、タグは記録されなかったものとして扱い、次のページで送り直す(表示には影響しない)。エラーは訪問者には見えない。したがって WAF のしきい値を絞りすぎると、**特定の送信元(たとえば NAT 配下の 1 つの会社)の露出(と履歴)だけが欠ける**という計測の偏りが生じる。しきい値の決め方は [デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨)。

**429 を数える**: タグは 429 を受けると、そのページで 1 回だけ `dataLayer` に `{ event: "ab_error", ab_error_type: "rate_limited" }` を push する(decision・目標・結果の送信・Mode B のどの 429 でも。同意の撤回の後は push しない)。GTM で GA4 に送れば、制限に当たったページビューの数を数えられる(設定の例は[サイト導入ガイド 12 節](site-install.md#12-datalayer-の契約と命名の規則))。数えられないものもある:

- 通信の失敗(ネットワークの切断・広告ブロックなど)では push しない
- edge をページと別のドメインに置く構成では、ゾーンの WAF の遮断(本文が `error code: 1015` の 429)をタグが読めない。WAF の応答には別のドメインのページから読むための許可のヘッダーが付かないので、ブラウザが通信の失敗として扱う。edge の binding の 429 は読めるように許可のヘッダーを付けているので、`*.workers.dev` の構成や別のドメインの構成でも数えられる

設置サイトと同じホストに edge を置く既定の構成と Mode B では、WAF の遮断も binding の 429 も数えられる。

### 新しい訪問者の記録の上限(サイト設定)

履歴の条件を使うサイト(`needsProfile`。Mode B を含む)では、edge が初めて来た訪問者の Visitor Profile を Durable Object に作る。ランダムな訪問者 ID を大量に送られると Profile が量産され、その書き込みと、後日の保持期限での削除が Durable Objects の日次上限を使う。これを抑えるため、サイトごとに 1 日に新しく記録する訪問者の数に上限を設けている。

- **値**: サイト設定の「一般」の「新しい訪問者の記録の上限(1 日あたり)」(管理者以上。API は `PATCH /sites/:sid` の `newProfileBudgetPerDay`、1〜100,000,000、`null` = 既定)。空欄の既定は、使用状況の設定の Cloudflare のプラン(11 節)に合わせて Free 20,000 / Paid 200,000。1 時間あたりはこの値の 10% まで。Free では、全サイトの合計にも 1 日 20,000 件の上限がある
- **超えたとき**: 訪問者にはテストがそのまま表示される(履歴の無い訪問者として判定する)。その訪問の Profile は作らず、履歴(閲覧回数・目標の達成・保存済みの割当)は記録しない。既に Profile のある訪問者の記録は続く。日の上限なら次の UTC 0 時、1 時間の上限なら次の正時(毎時 0 分)に戻る
- **上げたとき**: 止まっている間も約 1 分ごとに数え直すので、上限を上げると、新しい値が edge に届いてから 1 分ほどで記録が再開する
- **数え方の幅**: 作った後に数えるので、上限を少し超えて作ることがある。数える役の Durable Object に届かない間は止めない(記録を続ける)。上限は量を抑えるための目安で、厳密な上限ではない
- **防げる範囲**: Profile の書き込みと、後日の削除の量。Durable Objects への要求そのもの(判定のたびに Profile の Durable Object を呼ぶ分)は防げないので、要求の量はゾーンの WAF([デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨))で抑える
- 変更は次の公開を待たずに、設定の保存から反映される。edge は設定を最大 60 秒保持する。上限で止まっている間は約 1 分ごとに数え直すので、反映まで長くて 2 分ほどかかる

## 8. 既知の制約

仕様として受け入れている制約。回避策があるものは併記する。

- **SPA の `pushState` では再評価しない。** URL だけが変わって新しいコンテンツが挿入される画面遷移は検知しない。新しい評価はフルリロードを跨ぐ遷移でだけ走る
- **React・Vue 等が管理する要素は、フレームワークの再レンダリングで書き換えが戻ることがある。** `MutationObserver` で再適用を試みるが、仮想 DOM の差分がそれより高頻度・高優先度で走る場合は、再適用が追いつかない
- **CUSTOM_JS と HTML 内の `<script>` はページ読込ごとに 1 回だけ実行される。** SPA の再描画で要素が作り直されても、再適用されるのは HTML の DOM 挿入だけで、`<script>` は不活性のまま挿入される。CUSTOM_JS は再実行されない。consent の撤回 → 再許可でも再実行されない
- **CSS の変更は prehide(チラつき防止)の対象外。** `<style>` は decision の後に注入されるため、CSS だけで見た目を変えるエクスペリエンスはチラつく可能性がある。Exposure は対照群・処理群とも起動直後に出る(片側だけ発火する SRM を防ぐため)
- **Trusted Types(`require-trusted-types-for 'script'`)を強制するサイトでは HTML / CUSTOM_JS が動かない。** CSP の nonce は引き継ぐが、Trusted Types のポリシーは提供しない。失敗はその変更だけに隔離され、同じパターンの他の変更は動く
- **適用済みの変更は、consent の撤回で元に戻さない。** HTML 挿入 / CSS / CUSTOM_JS は原理的に巻き戻せないため。撤回後の最初のフルリロードから適用されなくなる
- **サイトを削除しても Visitor Profile は即時には消えない。** Durable Object は列挙できないため、`retentionDays` の alarm で自然に消えるのを待つ
- **エクスペリエンス / 目標を削除しても、Profile 内の割当と目標の達成回数は retention まで残る**(掃除されるのは閲覧したページの条件の記録だけ。どの公開中の配信条件からも使われなくなったページの条件は、公開中の設定がまだ Profile を使う(`needsProfile: true`。履歴条件か `persistAssignment` が残っている)ときに限り、次の公開の後の最初のアクセスで消える。Profile を使わなくなった設定では Profile に触れないので、`retentionDays` まで残る)
- **画面の幅の条件は、ページを開いた時点の幅で判定する。** 表示中に窓の幅を変えても判定し直さない。GA4 の端末の区分(User-Agent から決まる)とは定義が違うので、GA4 の `desktop` / `mobile` と件数は一致しない。タグを viewport の meta より前に置いたページ、viewport の meta が無いページでは幅が不明になり、画面の幅の条件を使うエクスペリエンスは配信されない([サイト導入ガイド 3 節](site-install.md#3-タグを置く))
- **「初回の訪問からの経過」は、訪問者 ID を発行した時点から数える。** 発行時刻は 1 時間単位に切り捨てて ID に入れるので、実際の初回の訪問より最大 1 時間早く数える(既に発行された ID の時刻は、そのまま使う)。Cookie の削除やブラウザの保存期限で ID が作り直されると数え直しになる。同意が必要なサイトでは、同意した後の最初の訪問が初回になる。発行時刻を持たない形式の ID(UUIDv7 形式でない、古い版で発行された ID)は「古い訪問者」として扱う(「N 日以上経過」の条件には当てはまり、「N 日未満」の条件には当てはまらない)
- **曜日・時間帯の条件はサイトのタイムゾーン**(サイト設定。既定 `Asia/Tokyo`)で判定する。訪問者の端末のタイムゾーンではない
- **設置タグのファイルの更新は、Durable Object の CPU 時間の上限を厳密に適用されると止まるおそれがある。** 現在は Free でも更新できているが、Cloudflare が上限を厳密に適用し始めたときは、公開は成功して配信ファイルの更新だけが止まる(公開の結果の `staticDeploy` が `pending`。サイトの上部の警告で気付ける)
- **`サブドメインをまたいだ共有` がオンなら、同じ登録ドメインのすべてのホストを信頼することになる。** 兄弟ホストは訪問者 ID の Cookie を読み書きでき、別の `Path` で植えられた同じ名前の Cookie は、同意の撤回でも消せない。他社が運営するサブドメインや、利用者が中身を作れるサブドメインにも ID が届く。そのようなサブドメインがあるなら、共有をオフにする。Mode B では、共有がオンの間は ID の Cookie が HttpOnly でなくなり、ページ上のすべてのスクリプトから読める(ID に含まれる初回の訪問のおおよその時刻(1 時間単位)も読める)。オフにすれば、Mode B は共有を足す前と同じホスト限定の HttpOnly に戻る
- **登録ドメインが違うドメインの間では、訪問者 ID は別になる。** ブラウザが Cookie を渡さないため。テストはどのドメインでも出るが、別の登録ドメインでの目標の達成は、参加したドメインの結果に入らない
- **Mode B で `/__ab/*` の Route が無いホスト(Cloudflare 外のドメイン)は、Mode A と同じ弱さを持つ。** ID を JavaScript で書くので、Safari ではそのホストにしか来ない人の ID は 7 日間訪れないと消える。edge が書いた ID は読むだけで書き直さない。ページの CSP を出しているサイトは、`connect-src` に edge のホストを足す([サイト導入ガイド 10 節](site-install.md#10-コードの変更と-csp))
- **配信するタグ(runtime と設定)が大きいと、公開の結果に警告が出る。** 警告は公開を止めない。初めて訪れたときの読み込みで、通信の往復が 1 回増えることがある。配信中のエクスペリエンスや変更を減らすと小さくなる

### Cron の回の結果を後から読む

control は 15 分ごとの定期処理(Cron)の回ごとに、各ジョブの結果(`ran`・`continued`・`failed` など)を 1 行の要約(`cron run`)にしてログに書く。エラーも同じログに書く。control は Cloudflare の Workers Logs を有効にしてあるので、これらを後から読める。

- **見る場所**: ダッシュボード → Compute(コンピュート)→ Workers & Pages → control の Worker(`wtt-control` か `wtt-control-<16 桁の 16 進>`) → Observability(日本語の表示は未確認)
- **読める日数**: 7 日(Free は 2026-11-30 まで 3 日)。それより前の回は読めない
- **残るもの**: コードが書く行(Cron の回の要約・エラー・警告と、一部の管理操作の記録)だけ。呼び出しごとの要求と応答の記録(invocation logs)は、設定(`apps/control/wrangler.jsonc` の `observability`)で止めている。すべての要求の URL(画像の公開ベース(`AB_ASSET_PUBLIC_BASE`)を control の `/dev-assets` にした構成では、画像を読み込む訪問者の要求も含む)を残さないためでもあるので、有効にしない。ただし、コードが要求の中で行を書いたとき(エラー・想定内の拒否の警告(書き込みの凍結中の `write_frozen`・`usage_not_configured` など)・一部の管理操作の記録(パスワードの再設定リンクの発行、初期設定の後始末))は、その行に要求の URL(path と query string を含む)が付いて残る。path には招待の ID のような、そのまま使える値が入ることがある。要求のヘッダー(API キーやセッション)は残らない。普段の要求では行を書かない
- **読める人を絞る**: 上のとおり、ログには要求の URL が残ることがあるので、Workers Logs を読める権限(Cloudflare のアカウントのメンバーのロールと、Workers Observability を読める API トークン)は、運用に要る人とトークンだけに絞る
- **管理画面の Worker(`wtt-admin` か `wtt-admin-<16 桁の 16 進>`)と edge では Workers Logs を有効にしない**: 管理画面の要求の URL には、パスワードの再設定のリンクのトークンと、ログインの直後に受け渡す使い捨てのコードが入るため。edge は訪問者の要求を受ける Worker で量も多いので、Workers Logs を有効にしていない
- **デプロイ専用の Worker**: `wtt-deployer` も Workers Logs を有効にしてあり、配信ファイルの配置の失敗と、runtime の更新の後の作り直しの失敗を書く。見る場所は ダッシュボード → Compute(コンピュート)→ Workers & Pages → `wtt-deployer` → Observability(日本語の表示は未確認)。control と同じく、呼び出しごとの記録は止めている
- **要約の行が無い回**: CPU や時間の上限で途中で打ち切られた回は、要約の行が残らない。15 分ごとの行が抜けている時刻は、その回が打ち切られたか、動かなかったことを示す
- **料金**: Cloudflare は 2026-12-01 から Workers Logs を Cloudflare Observability の料金体系に移す。移った後、Free はアカウント全体で 1 日 0.5 GB まで取り込み、超えた日は次の UTC 0 時まで取り込みを止める(課金はされない)。この枠は同じアカウントのほかの Worker のログなどと分け合うので、ほかが使い切った日は control の行も残らない。Paid は取り込みが月 50 GB まで込みで、保存の量も別に数え、どちらも込みの量を超えた分が課金される。control のログの量は、どちらの上限より桁違いに少ない(条件は 2026-10-25 に確認。[Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)・[Cloudflare Observability の料金](https://developers.cloudflare.com/observability/pricing/))

`config-cleanup` の回の終わりには、次の 1 行も残る(続きがある回でも出る)。

```text
cron config-cleanup: sites 2, kv deleted 48, bodies pruned 10 (today 10 of 5000, keep 20), skipped 0 unknown / 0 within keep / 0 over the daily cap / 0 over the run budget / 0 after a prune failure, rows_written 13, rows_read 1520, prune stmt ms max 2 total 4, size_after 5304320
```

`sites` は見たサイト数、`kv deleted` は KV の削除成功数、`bodies pruned` はその回に本体を消した版数。`today` は、その回で最後に成功した本体の batch の時点の、同じ UTC 日の累計(本体の掃除をしなかった回は回の初めに読んだ値。成否の分からない失敗の後は、実際の累計がこれより多いことがある。正はデータベースの `cron_cursors` の `config-cleanup:body-prune` の行)、`of` は日次上限、`keep` は保持する版数。`skipped` の内訳は、守る版が不明 / 版数が保持の数以下 / 日次上限 / その回の D1 の呼び出しの残りが足りない(KV の掃除で古い版を多く消した回。そのサイトの本体は次の日以降の回で消す)/ 本体の掃除の失敗後に見送ったサイト数(もともと消さないサイトは前の 2 つに数える)。`rows_written` は本体の掃除と日次の数の保存で書いた行数(KV の削除の印の更新は含まない)。`rows_read` は同じ 2 文が読んだ行数の和で、読み取りを減らす索引を適用した環境では、保持する本体・確定していない届く定義・配られたか判断できなかった届く定義の数に応じた読み取りになる(終了したテストで、配られたかを確かめられないまま残った届く定義も含む)。本体を消した履歴や、配られた・後の版に追い越されたと決めた記録が増えただけでは増えない。`prune stmt ms max` は本体の batch の各文の時間の最大、`total` はその回の全 batch の各文の時間の和(ms)。`size_after` は最後の本体の batch が返したデータベースの大きさ(バイト)で、時間や大きさを受け取れなかったときは `unknown`。本体の掃除を実行しなかった回は時間が 0、大きさは `unknown` になる。

回の要約には件数・時間・大きさだけを出す。サイトごとの失敗は、別のエラー行 `cron config-cleanup: site <id> failed…` で追える。本体の掃除の成否が分からない失敗の後は、その回の残りのサイトの本体を消さず、KV の掃除を続ける。次の実行でも、データベースに保存された日次の数を使って上限を守る。

## 11. 使用状況(Cloudflare の上限)

Cloudflare の Free プランには日次の上限があり(アカウント単位、毎日 UTC 0 時 = 日本時間 9 時に戻る)、尽きると翌日まで止まるものがある。止まる前に気付くための見方が 2 つある。

| 見方 | 手間 | 上限が尽きたとき | 要るもの |
|---|---|---|---|
| **ツール経由**(ホームの「使用状況」・左メニューの下の「設定」→「Cloudflare 使用状況」・`GET /usage`) | 簡単。判定と上限到達の見込みまで出る | Workers の上限が尽きると control も止まり、**見られなくなる** | 導入時に作るトークン(Account Analytics: Read)を control に入れておく |
| **Cloudflare を直接見る**(GraphQL Analytics API) | クエリを自分で投げ、上限と比べる | ツールの稼働に関係なく見られる(api.cloudflare.com は自分のアカウントの Workers の上限に数えられない) | 別の API トークン(Account Analytics: Read のみ)。control に入れたトークンは読み出せないので使い回さない |

### 設定(システム管理者)

左メニューの下の「設定」→「Cloudflare 使用状況」(「システム」の見出しの下)で変えられる。

- **見られる人**: すべてのメンバー(既定。ホームに要約が出る)/ システム管理者のみ。全員に見せても、出るのはアカウント全体の合計と本製品の内訳だけで、同じアカウントの他のプロジェクトの名前は出ない。顧客ごとにワークスペースを分けている導入では「システム管理者のみ」にできる
- **Cloudflare のプラン**: Free(既定)/ Paid。自動では判定しない(請求の権限を求めないため)。実際は Free なのに Paid を選ぶと、止まる前の警告が出なくなる
- **月額 $5 に含まれる量と比べる**(Paid のときだけ): 月額 $5 のプランに含まれる量(日次の資源は 30 日で割った 1 日分)と比べて表示するか。超えても止まらず、月の合計が含まれる量を超えた分が課金される。1 日の分を超えても、月の合計が含まれる量に収まれば追加料金はかからない。API(`GET /usage` の `reference`)は表示の設定に関わらずこの量を返す

### 判定

- Free: 日次の上限に対して 70% 未満「余裕あり」(`ok`)・70% 以上「注意」(`warning`)・90% 以上「危険」(`critical`)・100% 以上「上限に到達」(`exhausted`)。今日の消費のペースが続いた場合に上限に達する時刻も出す(UTC 0 時から 1 時間未満と、次のリセットより後になる場合は出さない)
- Paid: 日次の資源は判定しない(止まらないため)。月額 $5 に含まれる量と比べた結果だけを `within_reference` / `over_reference` で返す。保存量は D1 の 1 データベースあたり 10 GB だけを判定する。Durable Objects の 1 オブジェクトの上限(10 GB)など、オブジェクトごとの上限は判定しない
- D1 の 1 データベースの上限は、本製品のデータベース(`AB_USAGE_RESOURCES` に書いたもの)で判定する。書いていない、または書いた ID がどのデータベースとも一致しない場合は判定しない(「判定していません」と表示)
- 上限の値(2026-10-05 確認、[Workers の料金](https://developers.cloudflare.com/workers/platform/pricing/)・[Workers の上限](https://developers.cloudflare.com/workers/platform/limits/)・[D1 の上限](https://developers.cloudflare.com/d1/platform/limits/)):

| 資源 | Free の日次上限 | Paid の月の込み量 |
|---|---|---|
| Workers のリクエスト | 100,000 | 10,000,000 |
| Durable Objects のリクエスト | 100,000 | 1,000,000 |
| Durable Objects の行の読み取り / 書き込み | 5,000,000 / 100,000 | 250 億 / 50,000,000 |
| D1 の行の読み取り / 書き込み | 5,000,000 / 100,000 | 250 億 / 50,000,000 |
| KV の読み取り / 書き込み・削除・一覧 | 100,000 / 各 1,000 | 10,000,000 / 各 1,000,000 |
| 保存量 | D1 合計 5 GB・1 データベース 500 MB・Durable Objects 5 GB・KV 1 GB | 込み量 D1 5 GB・Durable Objects 5 GB・KV 1 GB(D1 の 1 データベースの上限 10 GB) |

### 上限が尽きたとき(Free)

| 尽きた資源 | 止まるもの | 動き続けるもの |
|---|---|---|
| Workers のリクエスト | 管理画面・control の API(Cloudflare の 1027 のエラーページ)・edge の判定とイベントの送信(`/v1/*`)・Mode B(`/__ab/*`)・配信ファイルの更新(デプロイ専用の Worker) | 設置タグのファイル(静的アセットで、Worker のリクエストに数えられない)・サイトの元の表示(どの場合も) |
| Durable Objects(リクエスト・行の読み書き) | `needsProfile` のサイトの判定(訪問者には元の表示)・テストの結果の記録(書く前に予算の Durable Object に問い合わせるため。タグは次のページで送り直す) | 管理画面・ほかのサイトの配信 |
| D1 の行の読み取り・書き込み | control と管理画面のすべて(閲覧・ログイン・API キーの認証・使用状況の表示を含む。D1 のクエリが失敗する)・テストの結果の記録 | edge の配信(配信は D1 を使わない)・サイトの元の表示 |
| KV の書き込み(1,000 / 日) | 公開(配る設定の書き込み) | 配信中の設定・管理画面での保存 |

訪問者のブラウザには、失敗したリクエストのたびに Console に `Failed to load resource …` が 1 行ずつ出る。対象は `/v1/*`・`/__ab/*` を使うサイトの判定と送信である。表示は元のまま壊れない。使用状況が開けないときは、上の「Cloudflare を直接見る」手順で確かめる。上限を超えたときの動きには、Worker を通さずオリジンへ流す fail open と、Cloudflare の 1027 を返す fail closed があり、本製品は fail closed を前提にしている(fail open ではオリジンの応答はサイトごとに違い、訪問者の ID を含む送信がオリジンに届くため)。この動きは設定ファイルでは持てない。`wrangler deploy` と配信専用の Worker の設定のスクリプトが作る Route は fail closed になる(実機で確かめた)。ダッシュボードでこの Route の動きを fail open に変えない。Custom Domain と `*.workers.dev` には選ぶ項目が無く、上限を超えると 1027 を返す。edge を別のドメインに置く構成では、edge は Custom Domain なので 1027 になる。

### Cloudflare を直接見るクエリの例

`deploy.md` 9 節 (b) と同じ方法で、Account Analytics: Read のトークンを使う。

```bash
curl -s https://api.cloudflare.com/client/v4/graphql -H "Authorization: Bearer $CF_ANALYTICS_TOKEN" -H 'content-type: application/json' \
  -d '{"query":"{ viewer { accounts(filter: { accountTag: \"<アカウント ID>\" }) { workersInvocationsAdaptive(limit: 100, filter: { date_geq: \"<今日 UTC>\", date_leq: \"<今日 UTC>\" }) { dimensions { scriptName } sum { requests } } durableObjectsPeriodicGroups(limit: 100, filter: { date_geq: \"<今日 UTC>\", date_leq: \"<今日 UTC>\" }) { sum { rowsRead rowsWritten } } } } }"}'
```

`workersInvocationsAdaptive` の `requests` の合計を Workers の日次上限と、`durableObjectsPeriodicGroups` の `rowsWritten` を Durable Objects の行の書き込みの上限と比べる。

## 12. テストの結果の記録

サイト設定の「一般」の「結果を記録する」を有効にしたサイトでは、テストの参加(訪問者がテストの対象の要素を見たこと)と目標の達成を、edge がこの導入の計測用のデータベース(D1 の `wtt-results`)に記録する。訪問者 ID はそのまま保存せず、鍵付きのハッシュにする。送る項目と保存の期間は[サイト導入ガイド 14 節](site-install.md#14-外部送信規律への対応)。

### サイト設定

- **結果を記録する**(管理者以上): 新しいサイトは、計測用のデータベースがある導入なら有効で作られる。既存のサイトは無効のまま。切り替えは「未公開の編集あり」に数え、次の公開から効く
- 記録するのは、**有効にした後に開始したテスト**だけ。開始のときにテストに記録の ID を振るので、有効にする前に開始したテストは、後から有効にしても記録されない(結果を見たいテストは、複製して開始し直す)。結果を記録しないサイトでテストを開始すると、開始の応答に「結果はツール上に残りません」の警告が付く(開始は止めない)
- テストの途中で無効にすると、無効にしていた期間はそのテストの記録が欠ける(管理画面は切り替える前に確認を出す)
- パーソナライズは記録しない(比べる相手が無いため)
- **参加者ごとの記録を残す日数**(7〜365 日、既定 90): 下の「参加者ごとの記録の保持と削除」
- 計測用のデータベースが無い導入では有効にできない(409 `results_store_missing`。作り方は[デプロイガイド 2.2](deploy.md#22-kv-と計測用のデータベースを作り設定に書く))
- 結果の数値・判定・注意の読み方は[テスト結果の読み方](experiment-results.md)にある(管理画面の「?」から同じ説明を読める)

### 評価計画と開始

テストの編集画面の「評価計画」のタブで、判定に使う目標・基準・期間・人数・判定の基準を決める(編集者以上)。結果を記録するサイトでは、開始の時点で評価計画を固定する。

- 必須は判定に使う目標だけ。決めないと開始できない(422 `evaluation_plan_incomplete`。基準の重みが 0 のときも同じ)。ほかの項目は既定値で開始できる(最低期間 14 日・最大期間 8 週・確率のしきい値 95%)
- 目標参加者数は、タブの「必要な人数の目安」で計算して入れることを勧める。空だと、人数に関係なく最低期間の終わりに判定する
- 開始のときの確認に、固定する内容の一覧が出る。結果を記録しないサイトでは「結果はツール上に残りません」と出る(開始は止めない。後から記録を有効にしても、そのテストは記録されない)
- 開始の後は、評価時点の前に、最低期間・最大期間を延ばす・目標参加者数を増やす(新しく設ける)変更だけができる。変更は理由とともに記録され、結果のタブに件数が出る。縮める変更と判定の基準の変更はできない(早く終えるときは終了し、基準を変えるときは複製して新しいテストにする)
- 評価計画の保存は「未公開の編集あり」に数えない(公開する設定に入らないため)
- 評価計画が参照している目標は、そのテストを終了するまで削除できない

評価時点の前の結果は「速報」で、判定を出さない。速報の数字で採用を決めない(何度も見るほど、偶然良く見えた値で決めてしまいやすい)。評価時点に判定を 1 回だけ出して記録し、以後は変わらない。

### 開始後のテストの編集

開始した後のテスト(配信中・一時停止中)は、評価時点の判定が何を測ったものかを 1 つに保つため、変えられる設定を限っている。パーソナライズはどの状態でも今までどおり編集できる。

| 編集 | 配信中・一時停止中のテスト | 終了したテスト |
|---|---|---|
| 配信率を上げる | できる | できない |
| 配信率を下げる・割当の固定を変える | できない(409 `test_setting_locked`。絞るときは一時停止か終了する) | できない |
| 変更・対象 URL・配信条件・判定に使う目標の定義 | できる。保存のときに確認が出て、公開した中身の配信を確かめた時点で「テスト中の変更」として結果に記録する | できない |
| パターンの追加・削除・重み・基準・判定に使う目標の選択 | できない(下書きのときだけ) | できない |
| メモ | できる | できる |

- オーディエンスと目標の編集では、参照している配信中のテストがあれば、件数を添えて確認が出る(公開すると、そのテストにも「テスト中の変更」として記録される)
- **終了したテストは読み取り専用**(メモ・採用の記録・削除だけができる。ほかは 409 `experiment_archived_readonly`)。変えるときは複製する
- 大きく変えるなら、途中で変えずに複製して新しいテストにする(途中で変えると、評価時点の判定は変更の前と後の期間を合わせたものになる)
- 公開してから、訪問者に新しい設定が配られたことを確かめるまでの送信は、前の定義で測ったものとして扱う。確かめた後も、ブラウザに残った前の設置タグの設定(最大 60 秒)の分は前の定義での送信が混ざる

### 終了と採用

テストの「終了して結果を記録」(管理者以上)で、採用したパターン(なしも可)とメモを記録する。

- 終了は、先に配信を止める公開を行い、その後で結果と採用を記録する。記録に失敗しても終了は取り消さず、「結果を記録できませんでした」と出る。結果の記録は自動で作り直され、採用は結果のタブから記録し直せる
- 採用は判定と関係なく選べる。基準に変更があるときだけ、基準の採用を選べる。変更の無い基準は「採用なし」で表す
- 「採用したパターンだけを表示する新しいエクスペリエンスも作成する」を選ぶと、終了の後に、そのパターンだけを表示するパーソナライズの下書きを作る(配信していた中身で作る。開始は人が行う)。複製に失敗しても終了は取り消さない(見出しの「複製」から作り直せる)
- 採用は、終了した後に結果のタブから記録し直せる(上書き。最後に記録した人と時刻が残る)。一覧に採用の要約が出る
- 評価時点の前に終了すると、終了の時点の値で判定し「評価時点前に終了」と付く。評価時点の後に終了しても、結果は評価時点の記録のまま変わらない
- 評価時点を過ぎると、結果の記録は止まるが、配信(パターンの表示)は終了するまで続く。結果のタブに「評価時点で記録を終えました」と出たら、終了して採用を記録する

### 参加者ごとの記録の保持と削除

- 参加者ごとの記録は、**記録を終えた時点(評価時点と終了の早い方)から、サイト設定の日数を過ぎた後、書き込みの予算に余裕のある日に消す**。削除は control の定期処理が UTC 23 時台に、その日の書き込みの予算の残りの範囲で、期限の古いテストから行う。1 日に消せるのは、Free で約 1.6〜2.4 万行、Paid(使用状況の設定の Cloudflare のプランが Paid。11 節)で最大約 29 万行まで(予算の残りが先に尽きれば、そこまで)。大きなテストは消し終えるまで数日かかる
- テストが実行中のままでも、記録を終えて期限が来れば消える。消した後に記録を再開することはない
- 消した後も、固定した結果(評価時点の記録、評価時点の前に終了したときは終了の記録)と採用の記録は残る(期限は無い)
- エクスペリエンスを削除すると、固定した結果・採用の記録・計画の変更の履歴はすぐに消え、参加者ごとの記録は削除の直後から順に消す。サイト・ワークスペースを削除したときも、そのサイトの参加者ごとの記録を順に消す
- 消した記録も、D1 の Time Travel の保持期間(Workers Free は 7 日、Workers Paid は 30 日)と、運用者が取った export には残る

### 計測用のデータベースの容量

計測用のデータベース(D1。Free は 1 データベースあたり 500 MB)の大きさを control が 15 分ごとに測る。

- 80% 以上になると、サイトの画面に警告が出る。テストの開始の応答にも、見込みで 80% を超えるときに警告が付く(開始は止めない)
- 95% 以上になると、結果の記録を止める(次の UTC 23 時まで。その日の削除が終わった後に測り直し、まだ 95% 以上なら止め直す)。止めた期間はテストの結果で「収集の停止」になる
- 空きを作るには、サイト設定の「参加者ごとの記録を残す日数」を短くするか、終わったテストを削除する。目安は、1 日の参加が 1 万人なら、最低期間 14 日・保持 90 日で約 170 MB

### 1 日の予算と止まったときの見え方

Cloudflare の Free の日次上限(Workers のリクエスト 10 万・D1 の書き込み 10 万行・読み取り 500 万行)はアカウント全体で、配信・管理画面と結果の記録が分け合う。守る順は「配信 > 管理操作(公開・終了など)> 結果の記録」で、結果の記録には 1 日の予算がある(既定は書き込み 7 万行。値は[デプロイガイド 2.2](deploy.md#22-kv-と計測用のデータベースを作り設定に書く))。

- 予算を使い切ると、その日は次の UTC 0 時(日本時間 9 時)まで結果を記録しない。訪問者の表示とエクスペリエンスの配信は変わらない。タグは送信を止め、0 時を過ぎてから送り直す
- 予算とは別に、control が 15 分ごとにアカウント全体の使用量(11 節の使用状況と同じ値)を見て、Free で Workers のリクエストか D1 の書き込みの行数が日次上限の 8 割に届いたら、同じく次の UTC 0 時まで記録を止める(UTC 0 時の直後の 00:00 の回は見ない。日が替わった直後は当日の使用量がまだ少なく、使用状況の取得も失敗しやすいため。次の 00:15 の回から見る)
- **Workers のリクエストの上限は事前に止められない。** edge は起動された時点でリクエストに数えられるので、15 分ごとの確認の間に 8 割を超えて上限まで使われることはありうる。使用状況の表示に Account Analytics のトークンが無い導入では、この確認は行われない
- **予算は導入全体で 1 つ**で、サイトごとには分けない。1 つのサイトへの送信が集中すると(悪意のある大量の送信を含む)、ほかのサイトの記録もその日の残りは止まる
- 止めた時間帯は記録してある(テストの結果を読むときに、記録が欠けた期間として扱う)
- **結果の記録は、配信が使う Durable Objects の枠を守る仕組みではない。** Durable Objects の日次上限もアカウント全体で、履歴の条件を使うサイト(`needsProfile`。Mode B のサイトを含む)の配信と結果の記録が分け合う。結果の記録の側は、Durable Objects に届かなければ書かずに止まるが、配信が Durable Objects の枠を使い切ること自体は防げない
- D1 の書き込みが失敗した送信は「収集できなかった送信」として数える(タグは次のページで送り直す)。ブラウザで止まった送信(CSP・広告ブロック・通信の失敗)と、Workers のリクエストの上限で edge が動かなかった送信は数えられない
- **Free で回せる目安は、1 日の参加の合計 約 1 万人**(全テストの合計。1 人が 2 本のテストに参加すれば 2 と数えるので、同時に実行中のテストの数だけ増える)。これを超えるサイトは Workers Paid(日次の上限が無い)を勧める。2 万人 / 日では、書き込みの予算をほぼ使い切り、予算を超えて記録が止まる日がありうる
- **Paid にしても、結果の記録の予算の既定値は変わらない(書き込み 7 万行)。** 参加 1 人の記録に 2 行(表と索引)、後の削除に 1 行を使い(目標の達成も同じ)、既定の予算で回せるのは 1 日の参加と目標の達成の合計 約 2 万まで。これより多いサイトは、予算([デプロイガイド 2.2](deploy.md#22-kv-と計測用のデータベースを作り設定に書く)の `RESULTS_WRITE_BUDGET`)を、1 日の参加と目標の達成の合計の 3 倍を目安に上げる。Paid の D1 の書き込みには日次の上限が無く、月の込み量(11 節の表)を超えた分が課金される。削除の量が増えるのは、使用状況の設定の Cloudflare のプランを Paid にしたときだけ
- 記録の締め切り(評価時点)は、edge に届くまでに最大 2 分ほど遅れる。目標参加者数に最低期間の後で届いたときは、届いたことを確かめる(結果のタブを開いたとき、または 1 日 1 回の定期処理)まで記録が続く。どちらの遅れの分も判定には入らないが、書き込みの予算と容量は使う

## 13. 画像の一覧

R2 を使う導入では、サイトの左メニューの「画像」に、そのサイトに上げた画像の一覧がある。画像はエクスペリエンスではなくサイトに属し、同じ画像をいくつものパターンで使える。パターンの IMAGE の変更は「画像を選ぶ」の窓で、この一覧から選ぶ。エージェントからの使い方は[エージェント向けガイド レシピ 1](agent-guide.md#レシピ-1-エクスペリエンスを作って公開まで編集者--管理者)の「画像」。

- **上げる・名前を変える・削除するのは編集者以上**。閲覧者は一覧と詳細を見るだけ
- **名前**は管理用で(既定はアップロードしたファイル名)、公開される画像の URL には入らない。サイトの中で重なると `(2)` のような番号を付ける。名前を変えても URL は変わらず、「未公開の編集あり」にもならない
- 一覧の札: 「使用 n」= 下書きの IMAGE か ATTRIBUTE の `src` で使っているパターンの数、「公開した内容で使用」= 公開したときの内容で使っている(そのエクスペリエンスを削除するまで削除できない)、「未使用」、「残しました」= 削除待ちにしたが使われていたので戻した画像(7 日の間出す)。HTML・CSS の変更の中だけで使っている画像は「未使用」と出る

### 容量の見方

一覧の画面の見出しの下に、サイトの使用量(「15 / 1,000 枚(うち削除待ち 2)· 307 MB / 1 GB」の形)と細い棒が出る。90% を超えると黄色になる。上限は既定で 1 サイトあたり 1,000 枚・合計 1GB で、導入の設定で変えられる(`AB_ASSET_SITE_MAX_COUNT`・`AB_ASSET_SITE_MAX_MB`。[デプロイガイド 3.4](deploy.md#34-varsappscontrolwranglerjsonc))。上限を超えるアップロードは断られる(409 `asset_quota_exceeded`)。

- 削除待ちの画像も、消えるまで(24 時間の後の定期処理まで)使用量に数える
- 縮小版は使用量に数えない
- 使用量は、その画面での操作の応答で更新する。ほかの人の操作は、画面を開き直すまで反映されない
- R2 の保存の無料枠(月 10GB)はアカウント全体で、サイトの上限とは別に数える

### 削除

詳細の「削除する」で、画像は**削除待ち**になり、一覧から外れる。すぐには消えない。24 時間の後の定期処理が、下書きのすべての変更・訪問者に届きうる公開の設定・公開したときの内容のどこにも、その画像が使われていないことを確かめてから、R2 のファイルと一覧の行を消す。使われていたら消さずに一覧に戻し、「残しました」の札を出す。

- パターンの変更(下書きの IMAGE・ATTRIBUTE の `src`)か、公開したときの内容で使っている画像は、削除のボタンを押せない(理由が詳細に出る)
- サイトの HTML に直接書いた URL・別のサイトの変更に書いた URL・JavaScript の中で組み立てた URL は、このツールからは見えない。そこで使っている画像を削除すると、表示されなくなる
- 削除待ちの画像は、新しく IMAGE の変更に選べない

### 定期処理 `asset-housekeeping`

control の 15 分ごとの定期処理(Cron)の 1 つ。画像の後始末を 1 回に次の順で行う。書き込みの凍結中は何もしない。R2 を使わない導入でも何もしない。回の結果は Cron の回の要約(10 節の「Cron の回の結果を後から読む」)に出る。

1. **削除の段**: 削除待ちにしてから 24 時間を過ぎた画像を、1 回に 5 枚まで確かめて消す(上の「削除」)。R2 のファイルを消せなかった画像は、一覧に出さないまま次の回にやり直す
2. **縮小版の段**: 一覧に出す縮小画像(幅 320px の WebP)を、Cloudflare Images の変換で 1 回に 4 枚まで作る。縮小版はアップロードの直後にも 1 回作り、そこで作れなかった画像をこの段が作る。1 日に作れるのは 384 枚まで。1 枚の作成に 3 回失敗した画像は、それ以上作らず、一覧に元の画像を出す。Images の binding(`apps/control/wrangler.jsonc` の `images`)が無い導入では、この段は何もしない

**Images の無料の枠を使い切った月**: Cloudflare Images の Free の枠(月 5,000 種類の変換)を超えると、新しい変換が断られる(課金はされない)。定期処理は断られた時点で、その月の末(UTC)まで縮小版を作るのをやめる。その間に上げた画像は、一覧に元の画像で出る(右下に「縮小版を作成中」)。翌月の最初の回から自動で作り始める。

**Images の binding を後から足したとき**: binding が無い間に上げた画像は、縮小版を作らない印(`skipped`)が付いている。binding を足して再デプロイした後に、次の 1 文で作り待ちに戻すと、定期処理が順に作る(1 日 384 枚まで、Images の枠の中で)。作成に 3 回失敗した画像(`failed`)を作り直したいときも、`'skipped'` を `'failed'` にして同じ 1 文を流す:

```bash
pnpm -C apps/control exec wrangler d1 execute wtt-control --remote --command "update assets set thumb_state = 'pending', thumb_attempts = 0, updated_at = CAST(strftime('%s','now') AS INTEGER) * 1000 where thumb_state = 'skipped' and deleted_at is null"
```

### まとめて上げるとき

画面のどこにでもファイルをドラッグ&ドロップすると、まとめてアップロードできる(1 枚ずつ順に送る)。送っている間も一覧と詳細は使える。送り終える前に画面を離れようとすると、確認が出る。

**一度に大量に上げるのは、1 日数千枚までを目安にする。** 画像 1 枚のアップロードで、D1 に約 6〜7 行を書く(一覧の行と索引・縮小版の記録)。Workers Free の D1 の書き込みの上限は、アカウント全体で 1 日 10 万行で、配信・管理操作・テストの結果の記録と分け合う(11 節)。1 万枚を 1 日で上げると、それだけで上限の半分以上を使う。縮小版はアップロードの直後に 1 枚ずつ作るが、Images の Free の枠(月 5,000 種類)を超えた分は翌月まで元の画像で出し、その後は定期処理が 1 日 384 枚ずつ作る。
