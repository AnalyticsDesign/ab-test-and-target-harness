# 導入構成の選び方

AI エージェントに導入を任せる場合は、この文書を読まなくてよい。[導入の質問](install-questions.md)に進む。やりたいことと今の環境を伝えると、エージェントが推奨の構成を示す。

手で導入する人や、推奨の根拠を知りたい人は、このガイドを使う。選べる構成はドメインの状態と Cloudflare の料金プランによって変わる。

1. 1 節の 4 つの問いに答える。
2. 2〜5 節で選択肢と、各構成で用意するものを確認する。
3. 6 節で選んだ構成を入力ファイルに書き、[デプロイガイド](deploy.md)へ進む。

迷ったら **構成 A(設置サイトのゾーンに載せる)× Free プラン** で始める。デプロイガイドの既定の構成はこれで、後から有料プランや control の守りを足しても作り直しは要らない(3 節・4 節)。

## 1. 決める順番

| # | 問い | 答えで決まること |
|---|---|---|
| 1 | 設置サイトのドメインを Cloudflare のゾーンとして使えるか | edge の置き方(構成 A / B / C)。ここだけは後から変えると設置タグの URL が変わる |
| 2 | 月の PV とピーク日の PV はどれくらいか | Free プランで足りるか、Workers Paid($5/月〜)にするか |
| 3 | 管理画面を何人で使うか、外部の AI エージェントに API を呼ばせるか | control の公開アドレス(`*.workers.dev` / 自分のドメイン)と、ログイン入口の守り方 |
| 4 | 画像の差し替え(IMAGE の変更)・Safari 対策(Mode B: サーバー発行 Cookie)を使うか | R2 のカスタムドメイン、`/__ab/*` の Route を足すか |

## 2. edge の置き方(問い 1)

訪問者のブラウザは、設置タグ(`/s/<siteId>.js`)を配信専用の Worker(`wtt-static`。静的アセットで、読み込みは Worker のリクエストに数えられない)から読み込み、判定と計測の送信(`/v1/*`)を edge に向ける。どちらも Cloudflare のゾーンに紐づけて同じホストで公開するのが既定。サイトのドメインを Cloudflare で管理していないときは、Cloudflare に追加した別のドメインに置く構成(B)を選べる。ドメインを用意せずに始めたい場合は、`*.workers.dev` で公開する簡易的な構成(C)を、制約を承知の上で選べる。

| | A. 設置サイトのゾーンに載せる(既定・推奨) | B. 別のドメインに載せる | C. Cloudflare にゾーンを持たない |
|---|---|---|---|
| 当てはまる状況 | 設置サイトの DNS が Cloudflare にあり、設置ホストのレコードがプロキシ有効(オレンジの雲) | 設置サイトの DNS は Cloudflare に移せないが、別のドメインを Cloudflare のゾーンにできる | Cloudflare にゾーンを 1 つも置けない |
| 可否 | 可 | 可 | **可(制約あり)**。前提 = Free アカウントで、止まって困る Workers が同じアカウントに無いこと |
| 公開の仕方 | `<設置ホスト>/s/*`(`wtt-static`)と `/v1/*`(edge)の Workers Route | edge は Custom Domain `<edge のホスト>`(例 `ab.example.net`)、`wtt-static` は同じホストの Route `<edge のホスト>/s/*`。`edge_address: custom-domain` | `*.workers.dev`(`edge_address: workers-dev`。`wtt-edge` と `wtt-static` の 2 つ) |
| タグと設置サイトの関係 | 同一オリジン。CORS 設定は不要 | 別オリジン。サイト設定の「ドメイン」の節の「タグを置くドメイン」(API は `domains`)にページのホストが要る(受け付ける Origin はこの一覧から決まる)。サイトが CSP を出していれば `script-src` と `connect-src` に `<edge のホスト>` を足す(設置タグと edge が同じホストなので 1 つ) | 別オリジン。サイトが CSP を出していれば `wtt-static` と edge のホストを足す |
| Mode B(サーバー発行 Cookie。Safari 対策の一方式) | 使える | 使えない(ページのホストに `/__ab/*` を置けないため) | 使えない |
| Cache Rule / WAF Rate Limiting Rule | 設置サイトのゾーンに作る | edge を置いたゾーンに作る。Cache Rule の条件のホスト名は `<edge のホスト>`。WAF Rate Limiting Rule の条件はパスだけで、[デプロイガイド 2.7](deploy.md#27-waf-rate-limiting-rule推奨) と同じ式 | **作れない**。万が一、悪意のある人がプログラムで大量のアクセスを送ってきた場合(タグのアドレスはサイトの HTML に書かれるので、誰でも知ることができる)、アクセスを制限できず、無料枠の日次上限を使い切られて当日の配信が止まる(Free なら課金は起きない) |

### 各構成の注意

- **A の前提の確認**: `curl -sI https://<設置ホスト>/ | grep -i '^server:'` が `server: cloudflare` を返せばプロキシ経由になっている。返さない場合、Workers Route は動かない(タグの URL がサイト本体の 404 になる)
- **DNS を Cloudflare に移すのはサイト全体に及ぶ作業**。ネームサーバーの変更、既存レコードの移行、SSL/TLS の暗号化モードの設定などが要り、この製品の手順の範囲外。サイトの管理者と相談して先に済ませる。ネームサーバーを移さずに一部のホストだけ Cloudflare に載せる方式(CNAME セットアップ)は Business プラン以上
- **B(別のドメインに置く構成)**: edge と設置タグを、ページと別のドメインのホスト(`<edge のホスト>`)から配る。手順はデプロイガイドの `custom-domain` のときの手順で、読む節は[デプロイガイドの冒頭の一覧](deploy.md#手で導入する最短の手順)にある。代償の一覧は[デプロイガイド 1 節の制約 (3)](deploy.md#1-前提と全体像)。別オリジンになるので、次の 5 つを引き受ける。
  - サイト設定の「ドメイン」の節の「タグを置くドメイン」(API は `domains`)に、ページのホストが要る(edge のホストではない)。サイトを作ると作成のときに入れたドメインが入る。ページのホストが複数なら足す
  - サイトが CSP を出していれば、`script-src` と `connect-src` に `<edge のホスト>` を足す。設置タグと edge が同じホストなので、足すホストは 1 つ([サイト導入ガイド 10 節](site-install.md#10-コードの変更と-csp))
  - Mode B は使えない。Mode B はページのホストに `/__ab/*` の Route を置く必要があり、edge を別のドメインに置くとそれができないため。この構成では Mode B による Safari 対策はできないので、Mode A か Mode C で運用する([サイト導入ガイド 8 節](site-install.md#8-mode-c-と-mode-b))
  - 設置タグを別のドメインのホストから読み込むので、ブラウザや拡張機能の追跡防止の機能に遮断されやすい
  - WAF の遮断(Cloudflare の 1015)は、別オリジンの構成では、タグが応答を読めない。WAF の応答には別のドメインのページから読むための許可のヘッダーが付かず、ブラウザが通信の失敗として扱うので、429 の通知(`ab_error` の `rate_limited`)が出ない。edge の上限(Rate Limiting binding)の 429 は許可のヘッダーを付けているので通知される([運用ガイド 7 節](operations.md#429-が訪問者に与える影響))

  edge を置くドメインはサイトのドメインとは別なので、別のドメインを Cloudflare に追加してもサイトには影響しない。ただし、そのドメインでメールなどのほかのサービスが動いているなら、ネームサーバーを切り替える前に、そのドメインの DNS レコードが Cloudflare に移っていることを確かめる(移っていないと、そのサービスが止まる)。ほかの Cloudflare アカウントで使っているドメインは選ばない。切り替えると、そのアカウントで動いているサービスに影響するため
- **C**: ドメインを用意せずに始められる簡易的な導入方法。期限や PV の上限は設けていないが、上の表のとおり Free が前提なので、評価のための導入に向く(3 節の CPU 時間)。上の表の制約を引き受ける。安定して使うときと、次のどれかに当てはまるときは、ドメインを 1 つ用意して(年 $10 前後)Cloudflare の Free ゾーンに追加し、設置サイトのゾーンに置く構成(A)か別のドメインに置く構成(B)にするほうがよい: 悪意のある人の大量のアクセスでその日の出し分けと計測が止まると困る / 1 日のアクセスが無料枠(10 万リクエスト)に近い。Safari 対策(Mode B)を使いたいなら A にする(Mode B は B でも使えない)。A へ後から移る手順は[デプロイガイド 2.8](deploy.md#28-ドメインありへの移行workers-dev--route)にあり、Worker・KV・サイト設定はそのまま使え、変わるのは設置タグの URL だけ。B へ移る手順はまだ無い

## 3. 料金プラン(問い 2)

### Free と Workers Paid

| | Free | Workers Paid |
|---|---|---|
| 月額 | Workers は $0。**日次の要求・CPU などの上限に達すると課金ではなく失敗する**。任意の R2 などは独立した料金体系 | **$5 はアカウントごとの最低額**。込み量(月 1,000 万リクエストなど)を超えると従量課金になる。Cloudflare の Workers の支出制限は要求・CPU の超過料金だけが対象で、ほかの資源や最低額は対象外 |
| 上限の単位 | **日次**(UTC 0 時にリセット)。Workers 10 万リクエスト/日、Durable Objects(DO。訪問者ごとの履歴などを保存する Cloudflare の機能)の行書込 10 万/日 など | 月次の込み量 |
| CPU 時間 | 1 回の起動あたり 10 ms。本製品は開発の段階で Worker の負荷が大きく、2026-11 の実測では、v0.9 の管理画面が Free で Cloudflare に時々止められた(v0.10・v0.11 は測っていない。v1.0 で CPU 時間は減ったが、重い要求が止められる可能性は残る。[運用ガイド 11 節](operations.md#cpu-の上限で要求が止められたときfree))。**Free での導入は評価のために使うことを勧める** | 1 回の起動あたりの上限が大きい(既定 30 秒)。**安定して使うならこちら**。ドメインなしの構成では、先にドメインを Cloudflare に追加する(2 節) |
| 目安 | 下の表の PV/日 と CPU・保存量を確認する | 下記の試算の前提では、Mode B は月約 1,000 万 PV、履歴条件・`persistAssignment` を使うと月約 80 万 PV で要求の込み量を使い切る。1,000 万 PV/月では、それぞれ約 $5 / 約 $7。結果の記録・画像・別オリジンの preflight は別 |
| 切り替え | — | ダッシュボード → Compute(コンピュート)→ Workers plans(Workers のプラン)。設定ファイル・再デプロイは不要で、いつでも移れる |

Free の要求数・書込行数から見た目安は次のとおり。月間 PV ではなくピーク日と比べる。動作を保証する PV 上限ではなく、CPU・保存量や同じアカウントのほかの利用分も確認する。

| サイトの構成 | 先に達する上限 | 目安 |
|---|---|---|
| 履歴条件・`persistAssignment` を使わない(`needsProfile: false`、Mode A / C)、結果の記録・画像配信なし | PV に比例する Worker の起動は無い。設置タグは無料の静的アセット | 訪問者への配信による Workers の要求上限は無い。管理操作・定期実行は別 |
| 履歴条件・`persistAssignment` を使う(`needsProfile: true`) | Profile の保存 1 回で 2 行(本文 + alarm)。予算確認・期限切れ削除にも DO の要求・書込が発生 | 目標 0.05 回/PV なら Profile 更新分だけで最大約 4.7 万 PV/日。追加分だけ下がる。新規 Profile の既定の予算(Free は導入全体で 2 万件/日)も別に確認する |
| Mode B を使う(履歴・結果の記録・画像なし) | Workers のリクエスト数(Cloudflare 経由のドメインで判定 1 回/PV) | 管理操作・定期実行などを除いて最大約 10 万 PV/日 |
| テストの結果を管理画面で記録する | 記録の予算は既定 7 万行/日。1 テスト、参加 1/3 回/PV・CV 0.05 回/PV・初回書込 2 行/件なら約 0.77 行/PV | 理論上約 9 万 PV/日。使い残しの枠・複数テスト・更新・削除などで下がる。超えた日は記録だけが止まり、配信は続く |

定期実行は control が 96 回/日、deployer が 24 回/日。公開・設定の保存・管理画面(admin)の SSR や API も資源を使う。admin → control → deployer の service binding は呼び先にも起動の記録が出るが、Paid の要求料金は最初の起動 1 回で、CPU は呼び先を含めて数える。DO の呼び出しは別に数える。静的ファイルは Worker を起動しなければ算入されない。Free の要求上限については、安全側に呼び先の起動も見込む。同じアカウントのほかの Workers と枠を共有するため、PV 以外の余裕も残す。

### 試算の前提と回数

[README の費用の目安の表](../README.md#前提)は、30 日/月、ピーク日が平均の 2 倍、全 PV が判定対象、目標送信 0.05 回/PV、新規 Profile 0.1 件/PV とした例。履歴ありでは、その後の保持期限切れも定常的に 0.1 件/PV 発生すると置いた。結果の記録・画像・CORS preflight・再試行・同意撤回の送信は含めない。管理操作などは月 4 万起動・DO 要求 1.2 万回程度、edge の CPU は 2 ms/要求、DO の処理は 20 ms/要求と置き、保存量は込み量以内とする。訪問者の実測から保証した値ではない。

| 訪問者の処理 | Worker の起動 | DO | D1・KV・R2 |
|---|---|---|---|
| 設置タグの静的配信 | 0 | 0 | 0 |
| Mode A / C、履歴なし | 0 | 0 | 0 |
| Mode B、履歴なし | Cloudflare 経由のドメインで 1/PV。ほかのドメインでは Mode A と同じ | 0 | 0(設定の KV 読取はキャッシュ欠損時に別途) |
| 履歴あり | Mode A / C は対象 URL で判定 1/PV、Mode B は毎 PV。さらに目標ごとに 1 | Profile 要求 1・読取 1・書込 2/判定または目標。新規作成の予算への報告と期限切れの alarm が追加 | D1・R2 は 0。KV は設定・配信内容のキャッシュ欠損時だけ |
| 結果の参加 | 訪問者 × テストの実行 × パターンごとに 1 回。ブラウザの保存が使えなければ増える | 記録の予算の確認で DO の要求が加わる(試算に含めない) | D1 は通常 batch 1 往復、初回 2 行書込(表 + 索引) |
| 結果の CV | 履歴なしは送信の束ごとに 1。履歴ありは goal、Mode B のページ表示目標は decision に便乗 | 同上。失敗時は失敗記録用 DO も使う | D1 は参加照会 + batch の通常 2 往復。目標 × 参加テストごとに初回 2 行書込。読取は参加件数などによる |
| 画像 | R2 のカスタムドメインなら 0。control の画像配信なら取得ごとに 1 | 0 | R2 Class B。カスタムドメインでは CDN に無いとき、control 経由では R2 取得ごと |

新規 Profile の予算への報告は、何件かをまとめて送る(最初の 1 件はすぐ送る)。Free はサイトと導入全体の 2 か所、Paid はサイトの 1 か所へ送るので、一律に「1 PV = DO 要求 1 回」にはならない。試算に含めない処理の分だけ、実際の回数は増える。上記の新規・期限切れの例では、Paid の DO 要求は約 1.17〜1.25 回/PV + 管理分となり、100 万回の込み量を月約 80 万 PV で使い切る。新規の割合や保持期間が変われば計算し直す。

KV の読み取りは、Worker が設定などを 60 秒キャッシュするので毎回は起きないが、世界各地への分散や Worker の入れ替わりで増えるため、PV あたりの固定値にはできない。訪問者の通常の経路には KV・R2 への書込は無い。結果記録の 7 万行の予算は、書込前は 1 件 3 行で見込み、書込後に実際の行数で精算する。先に確保して使い残した分は戻らないため、理論値の PV まで記録できる保証は無い。Free ではアカウント全体の Workers 要求または D1 書込が日次上限の 8 割に達した場合も、定期確認後に記録を止める。

### 上限を超えたとき(Free)

その日の残りは、Cloudflare が edge の Worker を実行しなくなる。**ページは元の表示のまま動き、エクスペリエンスが出ないだけ**になる(Exposure も GA4 に届かない)。control も同じ上限を共有するので、管理画面の操作も失敗する。設置タグのファイルは静的アセットなので、この上限に数えられない。

上限を超えたときの動きには、Worker を素通りしてサイト本体に渡す(fail open)と、Cloudflare のエラー 1027 を返す(fail closed)の 2 つがある。本製品は fail closed を前提にする。fail open にすると、訪問者の ID を含む判定と計測の送信がサイト本体のサーバーに届き、その応答はサイトごとに違うため。この動きは設定ファイル(`wrangler.jsonc`)では持てない。`wrangler deploy` と配信専用の Worker の設定のスクリプトが作る Route は、fail closed になる(実機で確かめた)。ダッシュボードでこの Route の動きを fail open に変えない。Custom Domain と `*.workers.dev` には選ぶ項目が無く、上限を超えると 1027 を返す。別のドメインに置く構成(B)では edge は Custom Domain なので 1027 になり、`*.workers.dev` の構成(C)も同じ。どちらも判定と計測の送信が失敗し、ページは元の表示のまま動く。

### 監視

Free は日次の利用量、Paid は請求期間の累計を、管理画面の「[使用状況](operations.md#11-使用状況cloudflare-の上限)」や Cloudflare の分析で確認する。Cloudflare の [Workers の支出制限](https://developers.cloudflare.com/workers/platform/spend-management/)は要求・CPU の超過料金に対して設定できるが、アカウント内のすべての Workers に作用し、DO・D1・KV・R2 や最低額は対象外。反映に遅延があるため、請求総額の厳密な上限にはならない。本製品自身が全資源の合計金額を見て自動停止する機能は無い。

### プランに関係なく要るもの

- **支払い方法の登録を求められることがある**: R2(画像の置き場)をアカウントで有効化するとき。無料枠内なら請求は発生しない([デプロイガイド 3.2](deploy.md#32-r2-と公開ドメイン))。**登録したくない場合は R2 を使わない構成(`asset_public_base: none`)を選ぶ**。画像アップロードと IMAGE の変更が無効になるだけで、画像の差し替えは ATTRIBUTE の `src` で行える(5 節)
- **導入の日に、Cloudflare の API トークンを作る(どの構成でも)**: 基本は、トークンを作るためのトークン(親トークン)を 1 本だけ作る。配信ファイルのデプロイ用(Workers Scripts の Edit だけ、期限なし。デプロイ専用の Worker にだけ置く)・使用状況の表示用などは、エージェントがそれで作り、使い終わった親トークンを消す。作ったトークンはアカウントに属するので、導入した人が外れても止まらない。既存のアカウントでは、親トークンの権限がそのアカウントのほかのサービスにも届くのを避けるため、管理者がデプロイ用などのトークンを Account API Token として直接作る方法が既定になる。親トークンが社内の規則で認められない・作る権限が無いアカウントでも、同じ方法を使う。管理者にも頼めないときの最後の手段は自分の User API Token で、作った人がアカウントから外れると、デプロイと使用状況が止まる。導入時に人に頼む作業の一部として、ほかの依頼とまとめて頼む([デプロイガイド 0.5](deploy.md#05-人に用意してもらうもの一度に集める))
- **ゾーンのプランは Free でよい**。Cache Rule と WAF Rate Limiting Rule(1 本、IP 単位、10 秒窓)は Free で作れる。ただし Free のレート制限ルールの条件に使えるのはパスだけで、ホスト名では絞れない。ルールを複数本に分けたい・期間を 1 分にしたいときは Pro 以上(Pro は 2 本)。Cookie やヘッダー単位で数えられるのは Enterprise だけ

## 4. control と管理画面(問い 3)

| 使い方 | control の公開アドレス | 入口の守り | 追加で要るもの |
|---|---|---|---|
| 個人、管理者 1 人 | `*.workers.dev`(既定) | 何もしない。ログインは Google アカウント(パスワードの経路は普段閉じている) | なし |
| 小規模チーム | 自分のドメイン(`control.<ドメイン>`) | ゾーンの WAF Rate Limiting Rule | ゾーン 1 つ(edge と同じゾーンでよい)。Free では edge 用のルールと 1 本を分け合う。Free は条件にホスト名を使えないので、同じゾーンのほかのサイトが control と同じパスを使っていないかを先に確かめる([デプロイガイド 7.2](deploy.md#72-2-waf-rate-limiting-rules)) |
| 外部エージェントに呼ばせる、到達自体を絞りたい | 自分のドメイン | Cloudflare Access(50 ユーザーまで無料) | Zero Trust の設定。エージェントはサービストークンを付ける。管理画面(admin Worker)から control への通信は service binding で、Access を経由しないので、admin には要らない。管理画面自体に Access を掛ける手順はデプロイガイド 4.5 |

自分のドメインを使う 2 つの守りは実機で検証していない。詳しくは[デプロイガイド 7 節](deploy.md#7-無認証入口の防御)。後から切り替えても、ユーザー・API キー・公開履歴はそのまま使える。

管理画面へのログインはどの構成でも **Google アカウント**で、入れるのは招待されたメールアドレスだけ。メール + パスワードの経路は普段閉じているので、**総当たりの標的になるパスワード入力が無い**(Google でログインできなくなったときだけ開ける手順が[デプロイガイド 8 節](deploy.md#8-非常時の入り方)にある)。本人確認と多要素認証は Google 側に寄るので、**管理画面に入る Google アカウントでは 2 段階認証を有効にする**。用意するものは Google の OAuth クライアント 1 つ(クライアント ID と クライアント シークレット。[デプロイガイド 3.3](deploy.md#33-secrets))。

**管理画面(admin)** は control とは別の Worker として Cloudflare Workers に置く(既定は `https://wtt-admin-<16 桁の 16 進>.<アカウントのサブドメイン>.workers.dev`)。admin は control を service binding(同じ Cloudflare アカウントの Worker 同士の内部の接続)で呼ぶので、**admin と control は同じ Cloudflare アカウントに置く**。この接続は control のゾーンを経由しないので、control に掛けた WAF・Access の対象にならず、ログインの回数は control が利用者の IP ごとに数える。自分のドメインに載せると招待・リセットリンクの見た目が整い、Access / WAF をゾーンで掛けられる(`admin_address: custom`)。運用者の PC でのローカル実行は開発用で、導入の選択肢ではない。

## 5. 付加機能(問い 4)

|---|---|---|
| 画像の差し替え(IMAGE の変更) | R2 バケットのカスタムドメイン(例 `assets.<ドメイン>`。ゾーンが Cloudflare にあること)。管理画面の画像の一覧(サイトに上げた画像を選んで使う)も R2 があるときだけ使える。一覧の縮小画像は Cloudflare Images の変換で作り、Free の枠(月 5,000 種類)の中で動く。枠を超えた月と、Images を使わない設定では、一覧に元の画像を出す([デプロイガイド 3.2](deploy.md#32-r2-と公開ドメイン)) | `dev-assets`(control 経由の配信)で暫定運用できる。画像の配信も Workers のリクエスト数を消費するので、本番で画像を使う前にカスタムドメインへ切り替える(使い始めた後に切り替えると、それまでの画像の URL が読めなくなる)。**R2 を使わない**(`none`)なら IMAGE の変更は無効になり、サイト上の既存画像の差し替えは ATTRIBUTE の `src` で行う |

## 6. 決めた内容をデプロイガイドへ渡す

決めた内容は `deploy-answers.yaml` の下段([デプロイガイド 0.2](deploy.md#02-構成を決める質問と入力ファイル-deploy-answersyaml))に書く(`owner_email` と、設置サイトのゾーンに置く構成(A)なら `install_host`、別のドメインに置く構成(B)なら `edge_host` は上段の行に書く。雛形の上段に最初から行があり、下段にもう 1 行書くと同じキーが 2 回書かれた誤りになる)。

| 決めたこと | 書く項目 |
|---|---|
| 構成 A の設置ホストとゾーン | `install_host` / `zone_name` |
| 構成 B(別のドメイン)の edge のホストとゾーン | `edge_address: custom-domain` / `edge_host` / `zone_name`(`edge_host` が属するゾーン) |
| 構成 C(ゾーンなし) | `edge_address: workers-dev`(`install_host` / `zone_name` は不要) |
| 画像の公開先 | `asset_public_base`(カスタムドメインの URL、`dev-assets`、または `none` = R2 なし) |
| control を自分のドメインに載せる | `control_address: custom` / `control_host` |
| 管理画面を自分のドメインに載せる | `admin_address: custom` / `admin_host` |
| 入口の守り | `control_protection`(`none` / `waf` / `access`) |
| edge の WAF ルールと、edge の Rate Limiting binding の値 | `edge_waf_rate_limit` / `edge_waf_requests_per_10s` |
| Mode B(サーバー発行 Cookie。構成 A のときだけ) | `dlite_hosts` |
| タグを置くページのほかのホスト(構成 A) | 上段の `extra_hosts`。Mode B を使うなら、そのうちゾーンの中のホストを `dlite_hosts` にも書く |
| 料金プラン | `plan`(`free` / `paid`。`paid` なら導入の前にダッシュボードで切り替える) |
